## The two verdicts mean opposite things — do not collapse them

- **`none` — no Payroc equivalent, or a target we could not determine.** The feature has to be
  redesigned, or the question escalated. Read the row before you say the capability is lost: some of
  these are checked absences, others are unresolved, with the target simply undetermined.
- **`config` — the capability survives; it is no longer something you *call*.** Payroc configures it
  at boarding, or it moves client-side into your own code. **Nothing is lost.** The integration
  changes shape, and the customer's action is a conversation with their implementation contact, not a
  rebuild.

Telling the developer a `config` row is a `none` row tells them they have lost something they have not.

## How to read a row

Rows are reproduced from their own mapping file — hedges, two-sidedness and confidence badges
included — not summarised. **Do not read a row's presence in this register as itself a confidence
signal.** A `none` row can be `verified` (a real, checked absence) or `unverified` (a question
still unresolved); this register does not distinguish the two by position, only by the badge
each row already carries. Read the badge.

**Where this register and a mapping file disagree, the mapping file wins.** Each section names the
mapping files its rows came from; go there for the full row and for anything corrected since.

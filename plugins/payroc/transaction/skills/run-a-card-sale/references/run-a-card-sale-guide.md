## Overview

The Payments API enables merchants to process card sales through their systems. A sale is a payment
where funds are captured immediately when the transaction is approved (`autoCapture: true`, which is
the default).

A single endpoint handles all card payments:

```
POST https://api.uat.payroc.com/v1/payments    (test)
POST https://api.payroc.com/v1/payments         (production)
```

The gateway returns a payment object containing a `paymentId`, which is required for all follow-on
operations (refund, reversal, adjustment).

---

## Three payment channels

| Channel | When to use |
| --- | --- |
| `pos` | Card-present, in-store. Card is read by a physical terminal (chip, swipe, tap) |
| `web` | Online / e-commerce. Card details entered in a web checkout form |
| `moto` | Mail order or telephone order. Agent manually enters card details on behalf of the customer |

The `channel` value affects which card entry methods are valid. For `web` and `moto`, `keyed` is
the standard entry method. For `pos`, use the appropriate hardware-specific method (`icc`, `swiped`,
`contactlessIcc`, etc.).

---

## Sale vs. pre-authorization

- **Sale** (`autoCapture: true`, the default): funds captured immediately on approval. This is the
  normal card-sale flow.
- **Pre-authorization** (`autoCapture: false`): funds held but not captured; a separate capture
  call is needed. Pre-authorizations are covered by a dedicated skill — this skill covers sales.

---

## Payment method types for card sales

For card sales the most common `paymentMethod.type` values are:

- **`card`** — raw card details (keyed, chip, swipe, contactless). Contains a `cardDetails` object
  with an entry-method-specific sub-object.
- **`secureToken`** — a saved card token from a prior tokenised payment. No raw card data is needed.
- **`singleUseToken`** — a single-use token generated by Hosted Fields. The token is exchanged for a
  payment in a single call; it cannot be reused.

---

## Key rules for the order object

- `orderId` must be unique per merchant — it's your reference for the transaction.
- `amount` is in the **lowest currency denomination** (e.g. cents for USD, pence for GBP).
  `5000` means $50.00 USD or £50.00 GBP.
- `currency` is an ISO 4217 code: `USD`, `GBP`, `EUR`, etc.

---

## What comes back in the response

On **201 Created**, the response contains:

- `paymentId` — save this immediately; it is required for refund, reversal, and adjust.
- `transactionStatus` — the current status of the payment (e.g. `authorized`, `settled`).
- `order` — echo of the submitted order with final amounts applied.
- `paymentMethod` — masked card information (last 4 digits, card type).
- `breakdown` — final itemised amounts if a breakdown was submitted.
- `links` — HATEOAS links pointing to available follow-on operations.

## Supported advanced features (not covered by this skill)

- **3-D Secure** — additional cardholder authentication for e-commerce. Covered by a separate skill.
- **Tokenization / credentialOnFile** — save a card for future use. Covered by save-a-payment-method skill.
- **Tips and taxes** — submit a `breakdown` object in the order.
- **Surcharging** — include `surcharge` in `breakdown`.
- **Dynamic currency conversion (DCC)** — submit a `dccOffer` in the order.
- **Offline processing** — submit `offlineProcessing` object for transactions taken when connectivity was unavailable.
- **Healthcare (HSA/FSA)** — submit `healthcareExpenses` array in `breakdown`.
- **Digital wallets** (Apple Pay, Google Pay) — use `paymentMethod.type: digitalWallet`.

## Cross-cutting facts

Read first: [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md) (transport, `AUTH S9 Melia`, `RESULT S9 Melia`, duplicate control, amounts, host) and [`identifier-translation.md`](identifier-translation.md) (`FIELD id`, `FIELD amount`, `FIELD token`, `FIELD payment_source_id`, `FIELD customer_id`, `FIELD order_number`, `FIELD metadata`, `FIELD currency`, `FIELD expiry`, `FIELD TimeStamp`, and the `DATA` rows). Those files own auth, results, duplicate control, currency, identifiers and cutover data, and are not restated here. Only facts local to this file follow.

1. **Melia carries four different things under the name `amount`, and none of them is Payroc's `order.amount`.** Payroc `order.amount` is the **total** of the transaction in the currency's lowest denomination, and `breakdown.subtotal` is the part before tax and fees. On Melia: (a) the `amount` you send on `POST /transactions` excludes the `tax` field and any surcharge: the gateway is charged `amount + tax + surcharge_amount`. Exception: `tax` is always taken from the request, so when `tax` is omitted and the merchant has automatic tax population and a tax rate, Melia treats `amount` as **tax-inclusive** and reports `amount - amount / (1 + rate / 100)`, rounded up, as the Level II tax; mapping that `amount` to `breakdown.subtotal` with no `taxes` drops the Level II tax the merchant used to send; (b) the `amount` on `PATCH capture` overwrites that same pre-tax `amount`, and the original `tax` and a recomputed surcharge are still added; (c) on `PATCH credit` with an `amount`, Melia compares the credit's `total` (`amount` plus the surcharge at the transaction's rate) with `authorized_amount - credited_amount` (the authorised **total**), and stores that surcharge-inclusive total as the credited amount; with no `amount`, the credit is the bare remainder `authorized_amount - credited_amount`, a surcharge on that remainder is still computed and sent to the gateway as a separate `surcharge` parameter, and the bare remainder is what is stored, so an omitted-amount credit's recorded total excludes a surcharge that was still sent (what the gateway did with the separate surcharge is not established); (d) a `GET /transactions` row carries one `amount`, which is either the pre-tax `amount` or the full total (`amount + tax + surcharge`) times 100; which of the two a row returns is not established. The full-total figure can come out one cent low (inferred; test fractional-cent amounts); rows created outside the API carry only the full-total figure. `GET /transactions/:id` returns the pre-tax attempted amount. The unit (cents) matches Payroc; the meaning does not. Every transactions row below that carries an amount says `amount` hazard or points here. The general rule is the `FIELD amount` row in `identifier-translation.md`. Never carry this rule to another iTransact surface: amounts are decimal dollars on xmltrans2, xmltrans, the CGIs and the order form.
2. **Melia and Payroc decide "settled" differently, and Payroc decides for you.** Melia calls a card transaction settled when its state is captured, postauthed, credited or voided **and** the merchant's most recent settlement time is later than the transaction's creation time; it then refuses a void (403) and allows a credit, and before that point it allows a void and refuses a credit (403). Payroc keys the same choice on the batch: `reversePayment` is documented for a payment "in an open batch", and `refundPayment` is documented to **reverse** the payment when it is still in an open batch and to return funds when the batch is closed. So code that already falls back from a refused void to a credit (the merchant's existing decision) collapses to one `refundPayment` call on Payroc; this does not license turning any other void into a refund, and the Melia guard that refused a credit before settlement does not exist. Payroc status values `ready` (in the open batch), `pending` (pre-authorised, funds not collected), `complete` (funds moved), `reversal` (cancelled) replace Melia's `status` and `settled` pair.
3. **Payroc has no customer resource.** Payroc's API documentation describes no customer or vault resource: none of its API paths concerns a customer or a vault, and the only stored-payment-method paths are the secure-tokens paths. Its guides describe no customer resource either. This is what Payroc's documentation shows, not a confirmed absence; confirm with your Payroc implementation contact if you need a customer-level object. What Payroc stores is a **secure token per payment method**, which embeds a `customer` object (name, addresses, contact methods) and `customFields`. A Melia customer with three cards becomes three unlinked secure tokens. This agrees with the `FIELD customer_id` row in `identifier-translation.md`.
4. **Payroc has no receipt-sending operation.** Payroc's API documentation describes no operation that sends or re-sends a receipt. This is what Payroc's documentation shows, not a confirmed absence. So a per-request "email the customer a receipt" flag has no Payroc counterpart in Payroc's documentation (see the `POST /transactions` and `resend_message` rows); confirm with your Payroc implementation contact how receipts are delivered for an API payment.
5. **Task-skill coverage.** `payment` is covered by `run-a-card-sale`; `payment` with `autoCapture: false`, `capturePayment` and `reversePayment` by `run-a-pre-authorization`; `refundPayment` and the refund follow-ons (including `reverseRefund`, `/refunds/{refundId}/reverse`) by `refund-a-card-payment`, which does **not** document `reversePayment`. `listPayments` is listed in the `run-a-card-sale` API reference, and `getPayment` only in that reference's route table; neither has a dedicated skill. `verifyCard` has none: no task skill in the transaction, notifications, reporting, funding or boarding skills documents it. `view-settled-transactions` covers `getTransactions` (settled, `GET /v1/transactions`), a different operation from `listPayments`.
6. **Swagger against behaviour.** The published swagger and Melia's actual behaviour disagree in places that touch these rows; follow Melia's actual behaviour. Here: the swagger marks the bodies of `PATCH capture` and `PATCH credit` as required, but `amount` is optional on Melia; the swagger lists six `status` values and Melia returns a seventh, `validated`, for an AVS-only check; the swagger declares only success responses, while Melia also returns 400, 401, 402, 403, 404, 405, 417, 429 and 500 (`map-protocol-auth-and-results.md`, `RESULT S9 Melia`); the swagger types `GET /transactions` as a single `Tran`, while Melia returns a list of rows. `resend_message` is not in the published swagger.
7. **Hedges that apply here.** payouts_api is **not routed per iTransact's routing configuration**; whether another host serves it is not established. Melia's own `/payouts` route is a different thing and is routed; `GET /payouts/:id` is in [`map-payouts.md`](map-payouts.md). Whether an ACH sale with `capture` works on Melia is not established. Whether any Melia route is called today is not established, so migrate callers either way.

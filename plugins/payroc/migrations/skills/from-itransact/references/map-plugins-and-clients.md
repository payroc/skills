# iTransact → Payroc: first-party plugins and samples, and third-party clients

> **Local snapshot — authoritative.** Payroc's own mapping from the plugins, samples and
> return relay iTransact shipped, and the third-party client libraries that speak to iTransact, to what
> Payroc offers instead. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct and fail in
> production.

## Cross-cutting facts

Transports, the nine authentication schemes, outcome signalling, duplicate control and the URL and HOST tables are in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md); identifiers and amount formats are in [`identifier-translation.md`](identifier-translation.md). Not restated. Facts local to this file:

1. **Payroc has no drop-in replacement for any plugin or client here, and its docs name none.** Payroc's documentation describes no osCommerce, VirtueMart, RediCart, ActiveMerchant or other cart or plugin integration, and the task skills name none either; that is not a confirmed absence. The only mentions of carts are in two pages that direct questions about WooCommerce, Magento, Shopify or OpenCart to a separate Payroc developer site, whose content you should check there. The same pages also direct "a solution that takes the customer away from their website" to that site, although Payroc's own documentation carries Hosted Payment Page guides; which one an iTransact merchant is meant to use is not established, so confirm it with your Payroc implementation contact. Those pages also direct questions on confirming a payment from the Hosted Payment Page or Payment Links to that site, and say Hosted Fields works only with the Payroc gateway, not the Worldnet gateway; so the receipt and validation mechanics in fact 3, and Hosted Fields availability for a given merchant, are for your Payroc implementation contact to confirm. The rows below say "re-integrate" and name the Payroc surface; none claims a plugin exists, and none claims Payroc has no plugin on the other site.
2. **Every cart plugin posts hidden form fields from the buyer's browser to an iTransact form handler**, so the Payroc pairing is a browser-side surface, not a REST call. The split page (`SPLIT /cgi-bin/mas/split.cgi`) pairs with the **Hosted Payment Page**; a card collected on the merchant's own page and posted to `ord.cgi` pairs with **Hosted Fields** (`createSession`, then `payment` with the single-use token). Whether the Hosted Payment Page in Payroc's documentation is the one an iTransact merchant is given is not established, so every row here that pairs an iTransact form or plugin with the Hosted Payment Page is `inferred`. The Hosted Payment Page has no operationId: it is a browser form post to `https://payments.payroc.com/merchant/paymentpage` (test `https://payments.uat.payroc.com/merchant/paymentpage`) that carries a SHA-512 `HASH` built with a terminal secret created in the Self-Care Portal. Task skill: `integrate-hosted-payment-pages`; Hosted Fields: `integrate-hosted-fields`.
3. **The return path changes shape.** iTransact (`ret_addr`, `ret_mode=post`, `passback`, `lookup`) names the return address and the echoed fields in each request. On the Payroc Hosted Payment Page the receipt page URL is a **terminal setting** in the Self-Care Portal, the result arrives as query parameters on a redirect (declines too, with `RESPONSECODE` `D`, `R` or `C`) with a SHA-512 `HASH` over `TERMINALID:ORDERID:AMOUNT:DATETIME:RESPONSECODE:RESPONSETEXT:SECRET`, the page returns no transaction type, and a separate **background validation** webhook (a POST to a validation URL, answered `OK`, retried for 96 hours, card payments only) confirms the payment server to server. The documented load request carries `TERMINALID`, `ORDERID`, `CURRENCY`, `AMOUNT`, `DATETIME` and `HASH`; no item, billing-address or return-URL parameter is documented in it or in the save-details and pre-authorization variants. Whether the page echoes a merchant-named pass-through field as `passback` did is not established (identifier-translation.md); confirm with your Payroc implementation contact.
4. **Hazards carried into the rows (behaviour change only).** (a) osCommerce module v1.1b2 formats the order total with a thousands separator; v1.2 does not (rows below). (b) The WooCommerce client marks an order complete from fields posted to it, and RediCart's `valid.cgi` treats any return request carrying a non-empty `email` as a completed order. (c) The osCommerce module accepts a return as paid when a `signature` field is merely present, without verifying it. On Payroc only a recomputed `HASH` or the validation notification is trustworthy; do not carry any of these rules over. The Payroc `HASH` is the first control that has to be recomputed on the merchant side.
5. **`CGI osc_ret/osc_ret.cgi` is not in any tagged iTransact release image since December 2021.** "Not in a tagged image" is a statement about builds, not about production: an untagged build is not ruled out, and whether production still serves the relay is not established. Migrate the carts that use the relay either way.
6. **Third-party clients are identified, not endorsed.** The rows say what each client sends and reads, not what any merchant runs. A client's code runs in the merchant's environment, so the pairing is "replace this client", never "Payroc supports this client". Their rows are `inferred`.
7. **The 2003 kit documents the gateway servlet.** `iTransact_XML_Transaction_Gateway_20031202.pdf` is the developer documentation for the gateway servlet, not for xmltrans2. Its chapter 2 overview, form structure and request list are summarised in the row below.
8. **Test card numbers, example keys, a hard-coded business name and similar values** appear in the sample archives and client code. Do not copy test card numbers, keys or business names from the samples.

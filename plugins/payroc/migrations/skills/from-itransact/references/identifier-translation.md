# iTransact → Payroc: identifier translation and field formats

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the identifiers and field
> formats an iTransact integration uses (transaction ids, tokens, customer, recipe and subscription ids,
> order and merchant references, account identifiers, amounts, currency, expiry and dates) to their
> Payroc counterparts, plus the data that must move at cutover. Per-row confidence is carried in the `C`
> column; the legend is in [`_sources.md`](./_sources.md). Last synced: 2026-10-11. Read mappings from this
> file, not from memory — a plausible-sounding mapping that isn't here will look correct and
> fail in production.

```text
IN:  The identifiers and field formats every other mapping file cites by name. Transaction identifiers
     used for follow-on operations and lookups (xid in ord.cgi and split-form results, xmltrans2 XID and
     OperationXID, xmltrans v1 XID, direct-CGI id and xid, Melia id and xid, servlet InternalId and
     ExternalId, Fife and translist xid, parentXid and child xids). Tokens (Melia POST /tokens, Checkout
     onToken, stored-card references in the servlet, the recurring billing_update token). Customer, recipe
     and subscription identifiers (cust_id, CustId, Melia customer, payment source and subscription ids,
     recipe names, the schedule key OperationXID, orig_xid). Order and merchant-reference fields per
     surface. Merchant and account identifiers the merchant's code sends (gateway id, vendor id, API
     username, MerchantAccountNumber). Formats: amounts, currency, card expiry, dates and timestamps. DATA
     rows: what must move at cutover.
OUT: Per-operation rows (which Payroc operation replaces void, trancred, AuthTransaction and so on): the
     domain files (map-xml-api.md, map-direct-cgis.md, map-json-api.md, map-gateway-servlet.md,
     map-recurring.md, map-transaction-reporting.md). Transports, authentication schemes, outcome
     signalling, duplicate control (Idempotency-Key) and the URL table: map-protocol-auth-and-results.md.
     How the data rows are carried out is not established; confirm with your Payroc implementation contact.
ADJACENT: map-protocol-auth-and-results.md holds transports, the nine auth schemes, outcome signalling and
     duplicate control. The domain files hold the per-operation rows that cite these identifiers. If your
     field is not in a table below, it is not absent from iTransact -- check the sibling, then SKILL.md's
     routing table, then check what your code sends.
```

Every row here is keyed `FIELD <name>` or `DATA <subject>`; other files cite these rows by that key.

## Cross-cutting facts

1. **No iTransact identifier can be passed to a Payroc operation, and no published Payroc process carries one across.** Payroc's API specification declares no field that takes an external, legacy, prior-transaction or migrated transaction id, and Payroc's published documentation describes no process that carries an iTransact transaction id across; the one documented way to record a legacy value is the token import. The import's `merchantref` (1 to 200 characters, unique per file and terminal, "how you identify a stored card after we import it") and optional `transactionReference` (0 to 128 characters, "reference for the original transaction used to create this token") are the only published places a legacy value can be recorded. This is not a confirmed absence: confirm with your Payroc implementation contact before relying on it. Whether iTransact is an accepted import source is not established (confirm with your Payroc implementation contact). **Old iTransact transactions stay on iTransact**: a follow-on against one cannot be run on Payroc.
2. **Payroc assigns some identifiers and the merchant assigns others, so the merchant must store more than it did.** Payroc assigns `paymentId` and `refundId`, each exactly 10 characters. The merchant assigns `order.orderId` (1 to 24, no pattern), `secureTokenId` (1 to 200), `paymentPlanId` (1 to 48) and `subscriptionId` (1 to 48). **Store going forward:** the `paymentId` from every `payment` response (and from the hosted page's `UNIQUEREF`), the `refundId` from `unreferencedRefund`, or from `refunds[]` of a `refundPayment` response on a settled payment (whether an open-batch `refundPayment`, a reversal, creates a `refunds[]` entry is not stated; map-json-api.md raises the same question, so confirm it with your Payroc implementation contact), the `secureTokenId` you chose, and the `subscriptionId` and `paymentPlanId` you chose. The legacy `xid` column cannot hold any of them (10 alphanumeric characters against an integer).
3. **An iTransact follow-on creates a new transaction with its own xid; a Payroc reversal or refund hands back the payment.** On the direct CGIs a void or credit acts on the parent named by `id` and returns the new transaction's xid; the parent keeps a list of its children, used to total earlier credits. Payroc's `refundPayment` is documented to reverse a payment that is still in an open batch, and returns the payment with a `refunds[]` array of refund summaries. For a settled payment the new `refundId` is read from `refunds[]`; the only response example is a `complete` payment with a `refunds[]` entry. For an open-batch payment the gateway reverses instead, and whether a `refunds[]` entry and a `refundId` are created is not stated (confirm with your Payroc implementation contact): do not assume `refunds[0].refundId` exists; read `getPayment` (unverified). Per-operation rows are in the domain files.
4. **Amounts differ per iTransact surface; do not assume one format.** xmltrans2, xmltrans, the direct CGIs and the order form take decimal dollars; Melia takes integer cents; the servlet takes either; Fife and translist return decimal dollars. Payroc `order.amount` on REST is an integer in the currency's lowest denomination, but the Payroc **Hosted Payment Page** takes `AMOUNT` as a Double. A port from a browser form to the hosted page keeps a decimal; a port from xmltrans2 to REST must convert. Rows in section 6.
5. **No iTransact surface takes a currency; Payroc requires one.** Across xmltrans2, xmltrans, the order form, the direct CGIs, Melia, the servlet's request mappings and Fife, no request names a currency. Where iTransact itself names a currency, it is `USD`. Which currency iTransact assumes on the card path is not established. Payroc `order.currency` is required.
6. **xmltrans2 requiredness is what the schema declares.** Whether runtime validation enforces it is not established. Rows below that depend on it say "declares". The xmltrans2 signature covers the literal text from the first `<Op>` to the first `</Op>` (map-protocol-auth-and-results.md); re-serialising a request in a dual-run period changes what was signed.
7. **Four surfaces are provisional or unsettled and their rows say so.** The gateway servlet is mapped **provisionally**: which integrations still call it directly is not established. The direct-call CGIs are not in any tagged iTransact release image since December 2021, which is a statement about releases, not about production; whether production still serves them is not established, so migrate callers either way. Split-form card results are **probably** `ord.cgi` results. Whether merchants still send requests to the deprecated xmltrans v1 endpoint is not established; migrate any caller either way.

### 2. Tokens and stored-card references

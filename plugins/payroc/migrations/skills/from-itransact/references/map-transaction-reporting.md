# iTransact → Payroc: transaction listing and export (translist), the pinauth SOAP service, and the Fife merchant API

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from iTransact's transaction-listing
> URLs (translist and its CSV, QIF, OFX and XML exports), the pinauth SOAP operation and the Fife merchant
> JSON API (`/h/merchant_api`) to what Payroc offers instead. Per-row confidence is carried in the `C`
> column; the legend is in [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this
> file, not from memory — a plausible-sounding mapping that isn't here will look correct in review and fail
> in production.

## Cross-cutting facts

Transports, authentication, outcome signalling, duplicate control, amounts and the sunset are stated once in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md); identifiers in [`identifier-translation.md`](identifier-translation.md). Only facts local to this file follow.

1. **These calls only read.** None creates or changes a transaction, so none needs an `Idempotency-Key` (the duplicate-control rows in map-protocol-auth-and-results.md do not apply). The one write-like effect is `send_receipt`, which overwrites a stored customer email and sends a mail (row below).
2. **Payroc has two families of list, and neither is the translist filter set.** Payment-level lists (`listPayments`, `listRefunds`, `listBankTransferPayments`) filter on a fixed set: `orderId`, `operator`, `cardholderName`, `first6`, `last4`, `tender`, `tipMode`, `type`, `status`, `dateFrom`, `dateTo`, `settlementState`, `settlementDate`, `paymentLinkId` (`listPayments`), plus `processingTerminalId`, `before`, `after`, `limit`. `listRefunds` takes the same set minus `tipMode`, `type` and `paymentLinkId`. `getTransactions` is the settlement list: it needs either `date` (the batch submission date) or `batchId`, filters `transactionType` (`Capture` or `Return`) and takes `merchantId`. So `getTransactions` returns settled activity only and cannot answer "list everything this merchant ran between two times", which both iTransact lists do. So the targets below lead with `listPayments`, as do the matching rows in map-protocol-auth-and-results.md.
3. **Filter crosswalk for translist (field by field; the `LOSS:` is carried in the list.do row).** Maps: `lastFour` to `last4`; `hfname` and `hlname` to `cardholderName` (one field, not two, and exact versus substring match differs); `transDateFirst`, `transDateLast`, `transTimeFirst`, `transTimeLast` to `dateFrom` and `dateTo`; `action` and `subAction` partly to `type` (`sale`, `preAuthorization`, `preAuthorizationCompletion`) with credits and returns on `listRefunds`; `status` to `status` with a different value set; `batchNumber` only on `getTransactions` as `batchId` (settled, a Payroc batch id); `instr` of `cc` to the card lists and `ck` or `eft` to `listBankTransferPayments` (pairing inferred, its filters not compared). Has no Payroc filter: `auth`, `avsCategory`, `avsResponse`, `cvv2Response`, `card` (card-type codes), `email`, `phone`, `ip`, `haddr`, `hcity`, `hctry`, `hstate`, `hzip`, `saddr`, `scity`, `sctry`, `sfname`, `slname`, `sstate`, `szip`, `entryMethod`, `extUserid`, `parentXid`, `recurXid`, `recurRecipe`, `recurStatus`, `total`, `transSource`, `xidFirst`, `xidLast`, the `force` and `void` actions, and the statuses `avs_fail`, `unknown`, `begun`. Payroc's payment-list parameters include no subscription, amount, authorization code, brand, card type or email filter. Payroc filters with no translist counterpart: `operator`, `tender`, `tipMode`, `settlementState`, `settlementDate`, `paymentLinkId`. The AVS and CVV outcomes are readable on each payment's `card.securityChecks`, so a caller that filtered on them must now fetch and then filter client-side.
4. **Paging differs in kind.** translist pages by `recordsPerPage` and `startingIndex`, required only for `list-html`, sorted ascending by `xid`, and the four export formats are not paged at all. Fife pages by `page` and `per_page` (both required), newest `xid` first, with no total and no next link. Payroc uses cursors: `before`, `after`, `limit` (default 10, maximum 100) and a response carrying `limit`, `count`, `hasMore` and `links`. You cannot jump to page N or to an xid offset; you walk `after` until `hasMore` is false. Payroc's documentation states no result order, and does not say whether `dateTo` is inclusive. A port that depends on newest-first (Fife) or oldest-first (translist) order must sort client-side, and should confirm the order and the `dateTo` boundary with your Payroc implementation contact or test them in the test environment.
5. **No export file formats in the Payroc API.** Payroc's published specification and documentation describe no report-export operation and no QIF, OFX or CSV report format; this is not a confirmed absence. The documentation mentions `csv` only as the token-import file format, and mentions neither `qif` nor `ofx`; QuickBooks is named only as a product feature of Roc Services and Roc Terminal+, not as an API. Payroc's documentation does say the Self-Care Portal can "Export reports easily for sharing or compliance purposes" and "Generate recurring reports for past transactions", but names no file format, so whether a portal export produces CSV, QIF or OFX is not established: confirm with your Payroc implementation contact.
6. **Who calls these.** iTransact's Android and iOS apps are known to call the two Fife operations (the apps are not rows in this skill); whether any merchant or third-party code also signs these calls is not established. No caller of translist or pinauth is known other than the merchant-facing sample pages and the service itself. Check what your code calls; who else calls translist or pinauth is not established. Migrate any caller either way.
7. **Unconfirmed behaviour that affects the rows below.** Whether translist validation covers the whole value of `outputFormat`, `action`, `subAction`, `card` and `hzip` is not established, nor is whether validation of `xidLast` takes effect; test whether a malformed filter is rejected or silently passes. Whether a reused HTTP session carrying earlier parameters into a later request affects a call is not established. Whether `list-qif` and `list-ofx` work for API callers is not established.

# iTransact → Payroc: the XML APIs (xmltrans2 operations and the deprecated xmltrans SaleRequest)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the two iTransact XML
> endpoints (the thirteen xmltrans2 operations and the deprecated xmltrans `SaleRequest` modes) to what
> Payroc offers instead. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

## Cross-cutting facts

Stated once in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md) and [`identifier-translation.md`](identifier-translation.md) and not repeated here: transport and bearer auth (the `TRANSPORT` and `AUTH` rows), the xmltrans2 signature over the literal first `<Op>` to first `</Op>` (map-protocol-auth-and-results.md fact 3), Payroc's 201-on-decline (map-protocol-auth-and-results.md fact 4), `Idempotency-Key` (the duplicate-control rows in map-protocol-auth-and-results.md: iTransact has none on either XML endpoint, Payroc requires one on every money-moving POST and PATCH), decimal dollars to integer minor units and the required `order.currency` (the amount rows in map-protocol-auth-and-results.md), and the xid to `paymentId` / `refundId` translation (the transaction-identifier rows in identifier-translation.md). Rows say "standard envelope" for the fields every Payroc money call needs: `Idempotency-Key`, `processingTerminalId`, integer `order.amount`, and for a new payment or unreferenced refund `order.orderId` (1 to 24 characters), `order.currency` and `channel`. Local to this file:

1. **Requiredness is what the schema declares.** iTransact's field documentation reports "required" from the schema rules. Whether the gateway enforces them is not established, so where a row depends on a check, test it, and a requirement that only the schema declares is never stated as enforced. The XSD does not appear to be loaded at runtime.
2. **Which operation runs is chosen by element presence, in a fixed order, and the first non-empty one wins.** Inside `AuthTransaction` the branch is chosen the same way (row `XML2 AuthTransaction`). Payroc has one `payment` operation and a flag, so the porting rule is to rebuild the choice, not to copy the element.
3. **Payroc follow-ons act on the same payment, and iTransact follow-ons create a new transaction.** `capturePayment`, `reversePayment`, `refundPayment` and `adjustPayment` all take the original `paymentId` and return `200` with the payment; `payment` and `unreferencedRefund` return `201`. Which id to store after each call is in identifier-translation.md (fact 3).
4. **TestMode answers are canned.** Every xmltrans2 transaction operation has a test path that returns `ok` with the placeholder `9999999999` and never contacts a processor. The triggers are `TestMode` exactly `TRUE`, a merchant-level test-all flag, or a billing first name equal to a merchant-configured test name. Payroc has no test flag; test traffic goes to the same host with a test API key (the `-test` `HOST` row in map-protocol-auth-and-results.md). A merchant whose account carried the test-all flag saw approvals that never reached a processor; on Payroc the same request gets a real outcome.
5. **Payroc-side absences below mean Payroc's API specification and documentation describe no such feature; they are not confirmed absences.** Each row that makes such a claim says what Payroc's documentation does and does not describe. Where a claim matters to your port and the documentation is silent, confirm it with your Payroc implementation contact.
6. **Reseller scope and merchant-lookup errors change.** On iTransact a reseller API key names its merchant through `TargetGateway`, and iTransact scopes that access more loosely than Payroc does (inferred; test it), so an integration that reaches merchants outside its own account through one key will not behave the same after the port. iTransact also answers a request for an unknown, offline or non-XML merchant with its own error key, before it checks the signature. A reseller integration, or code that branches on those error texts, must not assume either survives: the `CGI xmltrans2/xmltrans2.cgi` row carries the two behaviour changes.

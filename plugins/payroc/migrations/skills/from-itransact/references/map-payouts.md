# iTransact → Payroc: payouts (Melia `/payouts` and the payouts_api service)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from iTransact's payout calls
> (Melia's own payout routes on api.itransact.com and the separate payouts_api service) to what Payroc
> offers instead. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-10-11. Read mappings from this file, not from memory —
> a plausible-sounding mapping that isn't here will look correct in review and fail in production.

## Cross-cutting facts

Transports, the authentication schemes, outcome signalling, duplicate control, amounts and hosts are in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md); identifier translation is in [`identifier-translation.md`](identifier-translation.md). Facts local to this file:

1. **Two different things are called "payouts" on `api.itransact.com`, and only one of them is routed per iTransact's routing configuration.** Melia has its own payout endpoint with two routes (`GET /payouts/:id` and `POST /payouts`). iTransact's routing configuration sends every path on the production `api.itransact.com` host to Melia, so a request for `/payouts/...` reaches Melia. payouts_api, a separate service, is **not routed per iTransact's routing configuration**: no route for it appears in that configuration. Whether a payouts service runs behind another host is not established. Migrate any payouts_api caller either way.
2. **What Melia `/payouts` does.** `POST /payouts` takes `amount` in cents (with a per-merchant minimum and maximum) and exactly one of `card`, `token` or `payment_source_id`, plus optional `customer_id`, address, `order_number`, `metadata` and two receipt flags. It builds a payment source, creates a payout record owned by the calling merchant and completes it. The push step first sends an AVS-only request when the source has a CVV or an address and postal code, then a `PushFundsRequest` to the gateway, and stores the approval code and the gateway's internal id. iTransact then sends its own payout notification, whether or not the push succeeded. iTransact needs a separate "push" gateway id for the merchant on a payout request, and fails the request with a merchant-facing error if none is found. The endpoint does not check card push eligibility before pushing.
3. **What payouts_api does.** It registers "card acceptors" (the originator of payouts: fees, 16 velocity limits, a reserve balance) and "terminals" (a Visa merchant record with address and statement name) with the gateway, then pushes funds to a card number in a fixed sequence: reserve lock, velocity locks, a push-capability call, an amount-0 AVS-only validation, then the push. Both services therefore move money **from the merchant to a cardholder's card** through a Visa-style push. The order of the steps after the reserve lock is less certain than the rest of this fact.
4. **The compared behaviour, and why no Payroc funding operation matches it.** A payout to a card pushes an amount to a card number the caller supplies (the beneficiary is a cardholder, identified by a PAN), is authorised by the card network, and answers synchronously with an approval code. Payroc `createInstruction` "tells us how to distribute the funds from your merchants' transactions": it divides a merchant's **existing funding balance** among **funding accounts** (bank accounts) by `ACH`, in `USD`, and answers `accepted`, later `pending` and `completed`. The `paymentMethod` enum holds one value, `ACH`, and `currency` one value, `USD`. The beneficiary is a funding recipient, defined as "a business or organization that can receive funds but can't run transactions, for example, a charity". Different source of funds (a balance the processor holds against the merchant's settled sales, not a caller-driven amount against a reserve the caller funds), different destination (a bank account against a card), different rail, asynchronous against synchronous. So **none of the rows in this file is `direct`, and none is `absorbed` into a funding operation.** The funding task skills (`send-funds-to-a-merchant`, `set-up-a-funding-recipient`, `view-funding-activity`) own the bank-account flow and are named only as the nearest Payroc capability, never as a replacement.
5. **Payroc-side check for a push-to-card capability.** Payroc's published specification and documentation list no operation that pushes funds to a card number. This is not a confirmed absence: ask your Payroc implementation contact. Payroc's documentation also describes no card-acceptor, velocity, push-limit or reserve-balance setup. Its funding overview pages describe merchant settlement payouts to bank accounts, not card pushes. The only card-side signal is a BIN capability lookup, and it is outside Payroc's published API, so you cannot call it unless Payroc makes it available. It would be the counterpart of `PushFundsCapabilitiesRequest` (what the card can receive), not of the push. The nearest card-credit operation, `unreferencedRefund`, credits a card for a payment not linked to a prior transaction, only on `pos` or `moto` channels and "only on certain accounts"; it is a refund against the merchant's own card acceptance, not a payout, so do not use it as a replacement. Whether Payroc can enable a push-to-card payout for iTransact payout users is not answerable from Payroc's documentation: confirm with your Payroc implementation contact. The BIN lookup is not a published way to test for it.
6. **Authentication is a tenth scheme that the nine in map-protocol-auth-and-results.md do not list.** payouts_api reads `Authorization` as the Base64 of the API key alone: no scheme word, no signature, no second part; a missing header returns 401 `{"message":"Unauthorized"}`. Melia `/payouts` uses Melia's HMAC-SHA256 scheme (see map-protocol-auth-and-results.md). Neither maps to a Payroc credential beyond the one in that file: a bearer token.
7. **Duplicate control.** payouts_api documents `external_reference_id` as a "Unique reference ID from connecting system which can be used for lookups", and the two GET routes look a payout up by it. iTransact is not known to enforce uniqueness on it. Whether iTransact or the gateway rejects a repeated `external_id` is not established; test it. Melia `POST /payouts` has no client-supplied reference and is not known to check for duplicates. The duplicate-control rows in map-protocol-auth-and-results.md govern the Payroc side (`Idempotency-Key` on `createInstruction`).
8. **Identifier prefixes collide across services.** A payouts_api payout transaction id is `tr_<uuid>`; a Melia sale id is `tr_<base64url>`; a Melia payout id is `po_<base64url>`. So a `tr_` value alone does not say which service issued it, and `GET /transactions/:id` on `api.itransact.com` is Melia's sale lookup, not payouts_api's. Payroc ids (`paymentId`, `refundId`, `instructionId`) are a different shape and namespace (identifier-translation.md facts 1 and 2).

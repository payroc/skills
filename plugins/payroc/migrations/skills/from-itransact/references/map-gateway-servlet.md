# iTransact → Payroc: the Java gateway servlet (`/gateway/registered/GatewayServlet`)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the XML requests posted to
> the iTransact Java gateway servlet to what Payroc offers instead. This file is provisional: which
> integrations still call the servlet directly is not established. Per-row confidence is carried in the
> `C` column; the legend is in [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from
> this file, not from memory — a plausible-sounding mapping that isn't here will look correct
> and still fail in production.

## Cross-cutting facts

Transports, authentication, outcome signalling, duplicate control, amounts, hosts and the sunset date are in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md) (rows `TRANSPORT XML over HTTPS POST: gateway servlet (S13)`, `AUTH S13 servlet: username and password, or an X.509 certificate`, `RESULT S13 servlet: response roots in the body, HTTP 200`, `TRANSPORT duplicate control: gateway servlet (S13)`, `TRANSPORT amounts: servlet DollarAmount and CentAmount (S13)`). Identifiers are in [`identifier-translation.md`](identifier-translation.md) (rows `FIELD InternalId`, `FIELD ExternalId`, `FIELD MerchantAccountNumber`). They are not repeated here; read them there. Every transaction row below inherits from those rows: `+Idempotency-Key`, `+Authorization: Bearer`, `−username`, `−password`, `−xml` envelope, `+order.currency`, `DollarAmount` or `CentAmount` → integer `order.amount`, `ExternalId` → `order.orderId`, `MerchantAccountNumber` → `processingTerminalId`, `InternalId` → `paymentId`. Facts local to this file:

1. **S13 is in, provisional.** The servlet is a documented direct-integration surface for resellers and "technically advanced" merchants. Which integrations call it today is not established, and neither is which version of the servlet is in use; migrate any caller either way.
2. **The posted XML root is the row, and iTransact's documentation does not always spell the root the way the servlet accepts it.** The servlet accepts a registration, report or transaction (processor) request and refuses any other kind of request. Rows here are keyed on the roots the servlet accepts. For example iTransact's back-end documentation headings a report `SettlementListReportRequest`, and the servlet accepts `SettlementReportRequest`. What iTransact does with a root of one of those kinds that it does not recognise is not established; test it.
3. **Whether a transaction root works depends on the merchant account's processor, not on the servlet.** A request with a `MerchantAccountNumber` is routed by the merchant's stored processor to Finet, Monetra, Nova, Vantiv, Visa or Sage; `CardAttributesInquiryRequest` and `PushFundsCapabilitiesRequest` carry no merchant and go to Visa. Per-processor acceptance: Nova routes any address-verification request before any authorisation request, the batch, settlement and terminal-settle requests, and any id-based request, but routing is not acceptance: of the id-based requests it accepts credit, force, sale, void (of a sale, credit or force only) and post-auth, and refuses `CardRefundRequest`; Finet takes `CheckAuthRequest`, `CheckVerificationRequest`, `CheckCreditRequest`, `IdBasedCreditRequest` and `IdBasedVoidRequest` and refuses anything else; Visa takes `PushFundsRequest`, `AVSOnlyRequest`, `PushFundsCapabilitiesRequest` and `CardAttributesInquiryRequest`. Payroc routes on the terminal in the request, so the processor choice leaves the request. Where a row says "on a Nova merchant" it means this paragraph.
4. **Id-based follow-ons are typed against the original request, and the remote system must match.** iTransact refuses a mismatch with a `REQUEST_VALIDATION` error: credit needs an original of type sale, storage or force; force needs sale or pre-auth; sale needs sale, pre-auth or storage; void needs sale, credit, post-auth, pre-auth or force, and is refused when the original is already settled or voided (card originals: Vantiv and Nova refuse a settled one and say to issue a credit; Monetra has the same test, but whether iTransact ever marks a Monetra transaction settled is not established, so what the processor does with it is not established); post-auth needs a pre-auth; the refund check accepts a post-auth or sale original, but no processor then builds a refund (see `CardRefundRequest`). Per processor and original, the table is narrower: a Nova void needs a sale, credit or force; for a check original (Sage) a void needs a sale or credit and is refused only when already voided, not when settled, and an id-based credit on a check original runs no type or remote-system check. The Vantiv, Visa and Sage checks follow the same base rules. iTransact's back-end documentation says the gateway also checks that the request's `MerchantAccountNumber` equals the original's. The remote-system comparison is established; a merchant-account comparison is not, so do not rely on either reading of the documentation.
5. **Authorisation changes shape, and access is scoped more loosely on some processors (behaviour change only).** On Vantiv, Visa and Sage, iTransact scopes access more loosely than Payroc does, and an integration that relied on one credential acting across many merchants of that processor will not behave the same way after the port: a Payroc request is scoped by the credential and the terminal (how a Payroc key is scoped is not established; see [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md), and confirm with your Payroc implementation contact). The permission model itself (15 permission strings, one remote system per user) has no caller-settable Payroc counterpart: Payroc sets a `scope` on each API key's bearer token (fact 8a); see the administration rows.
6. **Card numbers arrive in two ways, and one has no Payroc counterpart.** A caller sends `CardAccountNumber` in clear over the connection, or sends `EncryptedCardAccountNumber` with `EncryptionKeyNumber`, produced with iTransact's PGP key flow (EncryptionServlet). iTransact's back-end documentation says clear numbers are PGP-encrypted before storage and no mechanism returns them, and `CardName` is wanted with the encrypted forms. Payroc's encrypted card variants require a `device` object, which is encrypted-reader data, not a merchant-held key. So the PGP flow is removed, not ported: send the card from a server in PCI scope, or tokenise it in the browser with Hosted Fields and charge the token (`integrate-hosted-fields`, `create-single-use-token`).
7. **Some Payroc operations have no dedicated task skill, so those targets name the operation alone.** `getPayment` and `listPayments` have no dedicated task skill: `integrate-payroc-cloud` documents both for the Payroc Cloud flow, and `run-a-card-sale` lists both, with their query parameters, in its schema reference, which is a reference and not that skill's own flow. `view-settled-transactions` is `getTransactions` (no `orderId` filter), a different operation. No task skill covers `closeBatch`, `verifyCard` or `listMerchantPlatforms` (`add-processing-account` covers processing accounts). Rows for these operations say "no dedicated task skill" or "no task skill"; read the operation in Payroc's API reference.
8. **Payroc-side absences used by more than one row.** These are absences in Payroc's published API specification and documentation, not confirmed absences. (a) Remote systems, certificates and permissions: Payroc's API documentation describes no remote systems, no client-certificate registration and no caller-settable permission; its only mentions are 401 and 403 error text, the token response field `scope` ("the resources you can send requests to with the Bearer token") and a least-privilege recommendation. So each API key's bearer token carries a Payroc-set `scope` of reachable resources, and nothing else here is settable by you. (b) Update of a merchant platform or processing account: the operations Payroc's specification lists for merchant platforms and processing accounts are all get or post (create, get, list and the like), none an update. (c) Push to a card, card acceptor, velocity limits: Payroc's API documentation describes no push to a card, original credit or payout to a card; the only related mention is BIN-level capability flags (see `CardAttributesInquiryRequest`); `map-payouts.md` fact 5 holds the full comparison. (d) Check or ACH verification scores: Payroc's bank-transfer documentation describes no score, guarantee or Equifax-style field. If a row's absence matters to your design, confirm with your Payroc implementation contact before treating it as final.

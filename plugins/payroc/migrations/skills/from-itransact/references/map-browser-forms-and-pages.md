## Cross-cutting facts

1. **Stated elsewhere, not repeated per row.** Authentication (`AUTH S3 ord.cgi`, `AUTH S12 Checkout`), outcome signalling (`RESULT S3 ord.cgi`), transports (`TRANSPORT HTML form post: ord.cgi (S3)`, `... split and buy-now forms (S4)`, `TRANSPORT browser script: Checkout (S12)`), duplicate control (`TRANSPORT duplicate control: ord.cgi reject_dups (S3)` and the split-form row), hosts (`HOST secure.itransact.com`, `HOST js.itransact.com` and the rest) and the URL table are in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md). Identifier and format rows (`FIELD xid`, `FIELD token`, `FIELD vendor_id`, `FIELD passback`, `FIELD Total`, `FIELD total`, `FIELD currency`, `FIELD when`, `FIELD cust_id`, `FIELD recur_recipe`) are in [`identifier-translation.md`](identifier-translation.md). This file adds only what is local to a browser form or page.
2. **Which Payroc browser surface replaces which iTransact page: the deciding questions.** Payroc has four browser-facing shapes, and none is a clone of an iTransact page. (a) **Hosted Fields** (`createSession`, task skill `integrate-hosted-fields`): card inputs on the merchant's page, the card never reaches the merchant's server; the browser gets a session token that lasts 10 minutes, then a single-use token that lasts 30 minutes and works once, and the merchant's server charges it with `payment`. (b) **Hosted Payment Page** (task skill `integrate-hosted-payment-pages`): the merchant's page POSTs six documented parameters (`TERMINALID`, `ORDERID`, `CURRENCY`, `AMOUNT`, `DATETIME`, `HASH`) to `https://payments.payroc.com/merchant/paymentpage` (test `https://payments.uat.payroc.com/merchant/paymentpage`); the `HASH` is a SHA-512 over `TERMINALID:ORDERID:AMOUNT:DATETIME:SECRET` with a terminal secret that the merchant sets in the Self-Care Portal and must never expose; it has **no operationId**, it is a browser form post outside the REST API. (c) **Payment links** (`createPaymentLink`, task skill `integrate-payment-links`): the merchant's server creates a link once and publishes its URL. (d) **`createSingleUseToken`** (task skill `create-single-use-token`): server-side tokenisation of card data the merchant's server already holds, never callable from a browser (it takes the bearer token). Choose by three questions: who holds the card data today (browser to iTransact: Hosted Fields or a hosted page; merchant server: `payment`), whether a server can build the request and keep a secret (Hosted Fields needs one to call `createSession`, the Hosted Payment Page needs one to sign; a static page has neither, so a link is the fit), and whether the URL is standing or per transaction (link or Hosted Payment Page). Whether the Hosted Payment Page in Payroc's documentation is the one an iTransact merchant is given is not established, so every pairing below that uses it is inferred.
3. **How a Payroc hosted page returns the result, against ord.cgi.** The Hosted Payment Page redirects the buyer's browser to one receipt URL per terminal (registered in the Self-Care Portal, not per request) and appends the response as query parameters, **on a decline as well**; the returned `HASH` is SHA-512 over `TERMINALID:ORDERID:AMOUNT:DATETIME:RESPONSECODE:RESPONSETEXT:SECRET`, so the other returned parameters (`UNIQUEREF`, `APPROVALCODE`, `CARDREFERENCE` among them) are not in the listed string (inferred: that the other parameters are unsigned follows from the listed string). A separate **background validation** POST reaches a validation URL for card payments only, retried with exponential backoff for up to 96 hours; the notification contract is in [`map-postbacks.md`](map-postbacks.md). A payment link has **no return address**: Payroc's payment-link schema and guides describe no redirect, return URL, callback or success URL. A buyer who must come back to the merchant's site therefore needs the Hosted Payment Page, not a link. The validation notification also carries `PAYLINK`, "the UUID of the payment link that the customer used to access the Hosted Payment Page", and a Payroc payment link opens "a payment page that we host" at `payments.payroc.com/merchant/pay-by-link?token=<UUID>`. So a card payment made through a link probably reaches the terminal's validation URL, but no page says so. The link's `paymentLinkId` is a 10-character id, not a UUID. Validation is card-only, while a link can take `bankTransfer`. Do not rely on a notification for link payments until a test-environment link payment shows one, and confirm with your Payroc implementation contact (inferred).
4. **Split-form card results are PROBABLY `ord.cgi` results.** The only final form action written out in iTransact's split templates posts to `/cgi-bin/rc/ord.cgi` on a non-production host; the JavaScript path's action is not known. Rows below say "probably". iTransact's production decline and error texts are not established, so no row maps a text; decide from `transactionResult.status`.
5. **Hosts that carry the split aliases.** `/cgi-bin/mas/split.cgi` and `buynow.cgi` are routed to the split page on the secure itransact, paymentclearing and staticgateway hosts; `split_old.cgi` only on paymentclearing and staticgateway; the gateway host routes only `/customers/split*`, `/payments/split*` and `/customers/buynow`, with no `/cgi-bin/` rule; a form that posts the `.cgi` path to the gateway host already fails, so migrate it as a split form either way. The `/jfet` prefix is routed on the paymentclearing and staticgateway hosts only; the secure itransact and gateway hosts have no `/jfet` route. The redi-check alias is in [`map-plugins-and-clients.md`](map-plugins-and-clients.md).
6. **Checkout has two builds and this file maps only one.** Checkout ships in two variants: the iTransact build requires `data-api-username` and the class `itransact-checkout-modal`; the IBX build requires `data-merchant-token` and the class `ibx-checkout-modal`. The IBX build is served as `jtlv2.js` from the IBX host (`https://gateway.ibxpays.com/api/v1/js/jtlv2.js`); in production it refuses to run unless loaded from that host and file name. So route by the script URL as well as the attribute: a page whose script tag `src` ends in `jtlv2.js` is the IBX build even when `data-merchant-token` is not yet visible. The from-ibx skill routes IBX browser tokenisation to its `REST POST /admin/jstoken` row (`createSession` with `scenario: tokenization` plus the Hosted Fields widget, verdict partial), and states that `POST /api/v1/json/reply/AdminGetToken` is the same capability. This file's Checkout row sends the IBX build to that row and does not restate it.
7. **Posted fields are not proof of payment (inferred).** Where a row says a posted field, or a signature over posted fields, does not prove payment, decide from the Payroc `payment` response or the verified Hosted Payment Page `HASH`.
8. **Hedges that apply.** The direct-call CGIs (see [`map-direct-cgis.md`](map-direct-cgis.md)) and `CGI pay_receipt/redirect/redirect.cgi` are callers to migrate either way: `redirect.cgi` is not in any tagged iTransact release image since December 2021, which does not mean production has stopped serving it (an untagged build is not ruled out); whether production still serves it is not established. iTransact is known to ship `nvpairs.cgi`, `ord.cgi` and `ord_receipt.cgi`. If your order forms set `ret_addr` to `/scripts/receipt/index`, see the `ord_receipt.cgi` row; check your own order forms for it. How iTransact's production serves that path is not established.

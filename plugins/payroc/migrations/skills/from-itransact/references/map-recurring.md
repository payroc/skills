# iTransact → Payroc: recurring billing (Melia recipes and subscriptions, billing-update pages)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from iTransact's recurring
> billing calls (the JSON API's recipe and subscription routes, and the cardholder billing-update pages
> and posts) to the Payroc API. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

## Cross-cutting facts

Transport, authentication, outcome signalling, duplicate control and amounts: [map-protocol-auth-and-results.md](map-protocol-auth-and-results.md) facts 1 to 8 and its duplicate rows (Melia has no duplicate control, so a retried `POST /subscriptions` is a second subscription; Payroc's `Idempotency-Key` is required on every POST and PATCH here except `deactivateSubscription` and `reactivateSubscription`). Every URL spelling for these keys is in the `URL` table of map-protocol-auth-and-results.md. Identifiers (recipe name, `sub_` id, `OperationXID` as a schedule key, `orig_xid`, `billing_update_token`, `payload_signature`): [identifier-translation.md](identifier-translation.md) sections 2 and 3. **Moving existing schedules is a data row, not a call:** `DATA recurring schedules` and `DATA stored cards` in identifier-translation.md section 7 and `DATA stored payment data and recurring schedules (cutover)` in map-protocol-auth-and-results.md. Payroc's documentation describes no import route for schedules (the published import is cards only, about 30 business days); whether Payroc recreates schedules for the merchant is not established, so confirm it with your Payroc implementation contact. This file does not restate those rows. File-local facts:

1. **iTransact's recurring model is one record; Payroc's is two layers, and Payroc's layers are created by API.** A recipe (`recur_recipe`: `name`, `period`, `every`, `billing`, `mail_text`, `allow_cust_update`, `hold_on_failure`, `deleted`, plus week-day and month-day sets) is built in the Control Panel only; Melia declares two GET routes for recipes and has no create route. A schedule holds the originating `xid`, the recipe, the remaining repetitions, the start date, the item set, a replacement card and customer, a hold flag and a failure-hold flag, and the surcharge flag and rate. Payroc needs a payment plan (`createPaymentPlan`, `set-up-a-payment-plan`: a merchant-assigned `paymentPlanId`, a `name` of 5 to 128 characters, `currency`, `frequency`, `type`, `onUpdate`, `onDelete`) and then a subscription (`createSubscription`: a merchant-assigned `subscriptionId`, the `paymentPlanId`, a `paymentMethod` of type `secureToken`, and a `startDate`). The `paymentMethod` carries the token value, `token` (12 to 19 digits, the receipt's `CARDREFERENCE` on the Secure Card Page), not the `secureTokenId`. The subscription may override the plan's name, description, amounts, `length` and `endDate`. Both ids are merchant-assigned strings of 1 to 48 characters. One plan per recipe is the natural pairing; whether to share plans is your design choice. The secure token must exist first (`save-a-payment-method`).
2. **Recipe-to-Payroc frequency table (this pairing is inferred; it is not a published crosswalk).** The legacy recipe form allows `period` `day` (any positive `every`), `week` (`every` 1 to 3, one or more weekdays), `month` (`every` 1 to 11, one or more days of month) and `manual` (a spread plus dated schedule rows); a second iTransact recipe definition accepts any integer `every` and validates only that a weekday or day-of-month is chosen. Payroc `frequency` is `weekly`, `fortnightly`, `monthly`, `quarterly`, `yearly` on plan and subscription, and `type` is `automatic` or `manual`.

   | iTransact recipe | Payroc | Note |
   |---|---|---|
   | `week`, `every` 1, one weekday | `weekly` | Payroc has no weekday field: the day follows `startDate` (inferred; not stated) |
   | `week`, `every` 2, one weekday | `fortnightly` | same note |
   | `month`, `every` 1, one day of month | `monthly` | iTransact anchors on the chosen day and runs a "last day" recipe (day 31) on the last day of short months; Payroc states no month-end rule, so confirm the collection day and the month-end behaviour in the test environment |
   | `month`, `every` 3, one day of month | `quarterly` | same note |
   | `month`, `every` 12 (the other recipe model only) | `yearly` | the legacy form stops at 11 |
   | `day` (any `every`), `week` with `every` 3 or several weekdays, `month` with several days or any other `every`, `manual` | none | LOSS: no Payroc value. Run your own scheduler with `payment` and `standingInstructions` (`processingModel` `recurring` or `installment`) or, for a monthly-or-slower pattern, collect each charge with `paySubscription` on a `manual` subscription, which accepts a payment only when one is due for the plan frequency |

3. **What the recurring billing job does, so a port can say what it loses.** iTransact's job bills only schedules that are not on hold and have repetitions remaining, skips merchants whose account is not open, and bills those the recipe says are due today; due-ness is a calendar test from the schedule's start date, with no catch-up for a day the schedule was held. It retries retryable failures within the day and puts a failure on hold only when the status is `error` and the recipe has `hold_on_failure`. Which errors count as non-retryable follows iTransact's own error classification, and whether production retries within a day is not established; migrate the schedules either way. A successful attempt decrements the remaining repetitions and, per merchant settings, mails the merchant and the cardholder and sends the recurring postback. **Payroc documents none of this:** Payroc's subscription and payment-plan documentation describes no retry within a day, no failure hold, no catch-up for missed cycles, no failure or success mail and no recurring postback. This absence is not confirmed. The only failure-related text is the status `suspended`, "if the customer misses payments". Do not port retry or hold behaviour as an assumption; confirm with your Payroc implementation contact what a declined cycle does.
4. **Payroc's PATCH on a subscription is documented as unable to change `frequency`, `type`, `currentState` or `paymentPlan`, and unable to delete `recurringOrder`, `description` or `name`.** **That list conflicts with the operation's own examples:** the realistic PATCH example replaces `/frequency` and the response returns `frequency: yearly`, and another example removes `/description`, so the list settles nothing either way. Keep the cautious routing: a change of schedule is a new subscription (deactivate the old one, create on a plan with the new frequency). Whether `PATCH /frequency` succeeds is not established; confirm it with your Payroc implementation contact or in the test environment, and until then do not rely on it.
5. **Payroc hosts a card-update page, but not iTransact's gated, mailed one. Two Payroc routes update a saved card; neither carries a mailed link, an identity gate, a per-recipe switch or a charge on a held schedule.** (a) *The Secure Card Page of the Hosted Payment Page* (no operationId: a form POST to Payroc's page, not an API operation; task skill `integrate-hosted-payment-pages`): `ACTION` `update` with the `MERCHANTREF` of the secure token to update, plus `TERMINALID`, `DATETIME` and a SHA-512 `HASH` built with the terminal secret, posted to `https://payments.payroc.com/merchant/securecardpage`. The request also takes `STOREDCREDENTIALUSE` (`UNSCHEDULED`, `RECURRING` or `INSTALLMENT`): Payroc's guide says to send it when the cardholder is saving card details and does not say whether `update` needs it, so send `RECURRING` (or `INSTALLMENT` for a fixed number of payments) for a schedule's card. The cardholder enters the details on Payroc's page and is redirected to the receipt URL the merchant sets in the Self-Care Portal, with the result as query parameters, also when saving fails. Your server builds the signed POST, so you still decide how a visitor is identified, and Payroc has no signed link. The `HASH` is a SHA-512 over terminal, `MERCHANTREF`, `DATETIME` and `ACTION`, built on your server but posted from the cardholder's browser; Payroc documents no expiry for `DATETIME` or the request `HASH` (not confirmed), so do not assume a captured signed form cannot be re-posted. Build it per page load, only for an authenticated cardholder. On the receipt, `A` means Payroc stored the details, `E14` and `E44` mean it did not store them (card, bank), and `E43` means the bank details were stored without being validated, so a code other than `A` is not always a failed update. **Inferred, not shown:** that `MERCHANTREF` is the REST `secureTokenId` (the page calls it the identifier the merchant assigns to the secure token), and that an update keeps the token value: a subscription stores the `token` (the receipt's `CARDREFERENCE`), not only the `secureTokenId`, so compare the receipt's `CARDREFERENCE` with the token the subscription holds after every update, and confirm the behaviour with your Payroc implementation contact. If `MERCHANTREF` is the `secureTokenId` (inferred, not shown), the `secureTokenId` survives by construction, because the update is addressed by it; whether the `token` value does is not stated. Whether this is the Hosted Payment Page an iTransact merchant is given is not established, so every pairing with it is `inferred`. (b) *Hosted Fields*: `createSession` (`scenario` `tokenization`, with the stored `secureTokenId` "to update a customer's payment details"; the session token expires after 10 minutes), then `accountUpdate` with the single-use token, or `updateSecureToken` for expiry, name, contact and address, which cannot change a card or account number. The secure token keeps its `secureTokenId`; whether `accountUpdate` keeps the `token` value that a subscription holds is not stated (inferred; confirm it with your Payroc implementation contact). `updateSecureToken` cannot change the card or account number, so the value is unchanged on that route.

   Payroc's documentation describes no customer portal, self-service billing page or mailed card-update link for cardholders. The cardholder-facing card-update route in the documentation is the Secure Card Page above (the guide's own wording is "update a customer's payment details"), plus the two Hosted Fields update pages. The Secure Card Page is documented in Payroc's guides, not in its API specification. The absence of a mailed link or gate is not confirmed.

   **Card check on the update.** None of the Hosted Fields documentation states a check of the new card. For the Secure Card Page, the only validation text is on the receipt page: response code `E14`, "We couldn't store the card details because we couldn't validate them", and the response `HASH` text. So Payroc validates card details when it stores them, but whether that is an authorization, an AVS check or only a format check, and whether `ACTION=update` runs it, is not stated; confirm it with your Payroc implementation contact. Do not read it as the check iTransact's page ran. `verifyCard` exists as a separate operation; no Payroc task skill documents it.
6. **Open points that apply to rows below.** The base URL of iTransact's mailed billing-update link is not established, and neither is whether the `/customers/billing_update/` path answers in production. Which recurring-postback sender production runs is not established. What iTransact does with a cross-site POST to the transparent endpoint is not established. These behaviours are not established and cannot be tested against iTransact before the shutdown (a Melia cancel on a failure-held schedule, the HTTP status of the transparent error pages, the first-charge day); test the Payroc equivalent instead.

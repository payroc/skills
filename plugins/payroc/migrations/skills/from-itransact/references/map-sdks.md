# iTransact → Payroc: official iTransact SDKs (node, PHP, PHP XML examples, Java)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the official iTransact
> client libraries (the node, PHP, PHP XML example and Java SDKs) to what Payroc offers instead.
> Per-row confidence is carried in the `C` column; the legend is in [`_sources.md`](./_sources.md).
> Last synced: 2026-11-03. Read mappings from this file, not from memory — a plausible-sounding mapping
> that isn't here will look right and fail in production.

## Cross-cutting facts

Transports, auth, outcomes, duplicates, amounts, hosts and the sunset are stated once in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md); id formats are in [`identifier-translation.md`](identifier-translation.md). They are not restated. Facts local to this file:

1. **What the three SDKs are.** `itransact-node` is a single-endpoint wrapper over Melia `POST /transactions`; `itransact-php` is the same plus four URL helpers; `itransact-java` is a generated client for Melia operations that cannot authenticate as shipped (fact 7). The PHP repo also ships four legacy XML example classes that post to xmltrans2. `itransact-node` is listed on npm at version 2.1.0, last published 2019-04-23; check it against the registry. The Java repo README is an archive notice. **Recognising SDK users in your code:** `require('itransact-node')`, the names `post_card_transaction`, `sign_payload`, `encode_username`, `getBaseUrl`, and the variable `ITRANSACT_ENVIRONMENT`; a `User-Agent` of the form `Node.js <version> - iTransact SDK <version>` in server logs; PHP `iTransactSDK::`, `iTTransaction`, `postCardTransaction`, `generateHeaderArray`; Java `io.swagger.client.api.*Api` and `setBasePath`.
2. **Payroc SDK equivalents, and where none is shown.** Payroc's generated SDKs are configured with a `Production` environment (older SDK releases may also offer a `UAT` environment, which points at the earlier `.uat.` test hosts; use `Production` with a test API key) and a bearer scheme whose token call is `POST /authorize`. The code samples in the Payroc task skills show: TypeScript `import { PayrocClient } from "payroc"` with `client.cardPayments.payments.create(...)` and `client.tokenization.secureTokens.create(...)`; Python `from payroc import Payroc`; Java `com.payroc.api.PayrocApiClient`; Ruby `require "payroc"`; C# `new PayrocClient()`. **The PHP sample is a raw Guzzle request, not an SDK call.** Payroc's documentation samples show no PHP SDK; call the REST API directly. The samples showing no PHP SDK is not proof that none exists; the specifiers above are only the ones the samples use. Confirm the published package names (npm, Maven, Packagist), the languages of Payroc's generated SDKs, and whether a PHP SDK exists, with your Payroc implementation contact.
3. **Signing code is deleted, not ported.** Node and PHP sign `JSON.stringify` or `json_encode` of the payload with HMAC-SHA256 and send `base64(username):signature`, which is the S9 scheme in `map-protocol-auth-and-results.md` (`AUTH S9 Melia: HMAC-SHA256 request signature`). Payroc's documentation describes no request signing (see that row). The PHP XML examples sign with HMAC-SHA1 over the `<AuthTransaction>` text (the S1 scheme, `AUTH S1 xmltrans2: ...`).
4. **A wrapper row is subordinate to the row it wraps.** A wrapper row (key `X ⇒ Y`) carries the wrapped row's verdict and target and only what the SDK adds or changes, and it does not contradict the row it wraps. If the two differ, follow the wrapped row; read it for the full behaviour.
5. **The `payment` required fields, stated once.** `payment` requires `channel`, `order`, `paymentMethod` and `processingTerminalId`, and `order` requires `amount`, `currency` and `orderId`; every POST also needs an `Idempotency-Key` (the duplicate-control rows in `map-protocol-auth-and-results.md`). Where a row's delta says "+payment required fields" it means those. No iTransact SDK call carries a currency, a terminal or a channel.
6. **A Payroc payment has no per-payment receipt flag.** Payroc's API documentation describes receipts only as `receiptNotifications` (`emailReceipt`, `smsReceipt`) on processing accounts and terminals, a device printing capability, and a billing `paymentReceipt` schema; none is on the payment request. So the iTransact `send_merchant_receipt` and `send_customer_receipt` request flags have no Payroc request counterpart; receipts are terminal configuration. If you need per-payment receipt control, confirm with your Payroc implementation contact.
7. **The Java client, as shipped, is not a working client; this applies to every Java row.** (a) The default base path is a placeholder, `https://itransact.com/path`, repeated in the setter doc; the client never sets the real host, so a caller must call `setBasePath`. **Anyone who used the SDK unchanged was never calling the API**; where that placeholder host leads is not established. (b) No authentication is wired: the client sends no credentials. Melia refuses a request with no credentials, so each call from the shipped client would be refused (inferred; test it). (c) The operations collect parameters as form fields with bracketed keys such as `card[number]` but declare content type `application/json`, and the client builds a form body only for form-urlencoded or multipart types, so POST and PATCH calls send an empty body (inferred; test it). (d) The list operations are typed as a single object, for example `public Customer getCustomers()`, while Melia returns a collection, so deserialisation of a list would fail (inferred; test it). (e) Card number and CVV are typed `Integer`, so long card numbers do not fit and a CVV loses leading zeros (inferred; test it). Because of (b) and (c), a merchant that depended on this client cannot have been sending live traffic through it; what to port is whatever the merchant wrote around it, so check what your own calling code sends.

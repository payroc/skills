# iTransact → Payroc: postbacks (the merchant's endpoint that receives an iTransact postback)

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the endpoints a merchant
> runs to receive an iTransact postback (recurring, order, billing-update and autostatus senders, and
> the postback test CGI) to what Payroc offers instead. Per-row confidence is carried in the `C` column;
> the legend is in [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file,
> not from memory — a plausible-sounding mapping that isn't here will look correct and fail in
> production.

```text
IN:  The endpoint a merchant runs to RECEIVE an iTransact postback, one row per sender: the recurring
     postback (PGP-signed), the order postback from ord.cgi, the Fife postback (including the
     transparent billing update reply that the same Fife code sends), the autostatus postback, and
     postback_test.cgi.
OUT: Result postbacks of the direct-call CGIs (void, credit, postauth, tranforce, trancred, tranretry),
     the mreg, mcc and mck postbacks, and osc_ret.cgi are not rows here. Event subscription management
     itself (createEventSubscription and the other five operations) is a Payroc surface, not an
     iTransact call. How a request authenticates, outcome signalling, duplicate control and amounts:
     map-protocol-auth-and-results.md. Identifiers: identifier-translation.md.
ADJACENT: map-direct-cgis.md holds the direct-call CGIs, whose own result contract is separate from
     these rows; map-browser-forms-and-pages.md holds the ord.cgi request side (ret_addr, ret_mode,
     lookup, passback); map-recurring.md holds the schedule and the billing update request side;
     map-plugins-and-clients.md holds plugin relays. If your call is not in the table below, it is not
     absent from iTransact -- check the sibling, then SKILL.md's routing table, then check a sample of
     what your code sends.
```

## Cross-cutting facts

Authentication, outcome signalling, duplicate control, amounts, hosts and the sunset are stated once in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md); identifiers (`xid`, `orig_xid`, `cust_id`, `passback`, `recur_recipe`) once in [`identifier-translation.md`](identifier-translation.md). Facts local to this file:

1. **Payroc has two push mechanisms and neither carries an iTransact postback's trigger.** (a) Event subscriptions: `createEventSubscription` registers a webhook, and Payroc's events list names four event types, all with Resource `Boarding`: `processingAccount.riskStatus.changed`, `processingAccount.signature.signed`, `processingAccount.status.changed`, `terminalOrder.status.changed`. Payroc's API documentation also mentions a fifth, `paymentIntent.status.changed`, for terminal-order payment intents (also boarding scope). None of the five is a payment, subscription or token event. Payroc publishes no exhaustive list of event types, so the docs list plus that one mention is the list to work from. (b) Hosted Payment Page background validation: a POST to a validation URL after each card submission on the Hosted Payment Page, approved or declined. Neither fires for a recurring charge, a billing update or an API `payment`. This rests on Payroc's documentation, not a confirmed absence: Payroc's API documentation describes no payment, subscription or token event and no webhook on the subscription, payment-plan or payment operations. If you need push delivery for any of these, confirm with your Payroc implementation contact whether an event type exists that the documentation does not list.
2. **Signing is a shared secret or a hash, not a signature, on every Payroc push.** Event subscriptions: you choose a `secret` (16 to 64 characters) and Payroc returns it in a `Payroc-Secret` request header on each webhook call; the `set-up-event-subscriptions` skill tells the receiver to compare it in constant time. Payroc's documentation describes no webhook signature, HMAC or digest scheme; the only signing it mentions is PGP for data migration and token import, and signature capture. Payroc names no scheme for a webhook signature header; confirm with your Payroc implementation contact whether any webhook is signed beyond the echoed `Payroc-Secret` header. Background validation carries a `HASH`, SHA-512 over `[TERMINALID]:[ORDERID]:[AMOUNT]:[DATETIME]:[RESPONSECODE]:[RESPONSETEXT]:[SECRET]`; the documented order names six fields, so a parameter outside it (for example `UNIQUEREF`) is not in the hash as documented (inferred). iTransact's signature on its postbacks is conditional and differs by sender, so no iTransact signature check ports; verify the Payroc HASH.
3. **Delivery behaviour differs on every sender.** iTransact: the recurring and order senders make one attempt and treat 2xx or 3xx as success; Fife retries every 10 minutes with a limit of 5 and counts only 2xx as success; the transparent-update reply makes one attempt. Payroc events: a non-200, or no response within 15 seconds, is retried five times, then the support address is emailed; the retry interval is not stated in Payroc's documentation, so confirm it with your Payroc implementation contact. Background validation: no `OK` in the body means exponential backoff over 96 hours, then the transaction is set to expired and the merchant emailed. Payroc may deliver an event more than once; the `set-up-event-subscriptions` skill says to de-duplicate on the CloudEvents `id`.
4. **Payload format changes and the receiver must be rewritten, not re-pointed.** Every iTransact sender posts `application/x-www-form-urlencoded`. A Payroc event is a JSON CloudEvents body (`specversion`, `type`, `version`, `source`, `id`, `time`, `datacontenttype`, `data`); background validation stays form-encoded but with different field names (`UNIQUEREF`, `RESPONSECODE`, `HASH`).
5. **Deployment: whether production runs each sender is not established.** iTransact is set up to send the recurring postback and the Fife postback, and the autostatus postback is switched off, so a receiver for it has no sender; what production actually runs is not established. `ord.cgi` is part of iTransact's current release; `postback_test.cgi` is not in any tagged iTransact release image since December 2021, which says nothing certain about production (an untagged build is not ruled out). Migrate every receiver either way.
6. **Request-side settings move from the request or the account into Payroc configuration.** iTransact lets a merchant pick the target per order (`ret_addr`) or per account (`ret_post_addr`, `ret_on_recur`). Payroc fixes a webhook target in the subscription and the validation or receipt URL per terminal in the Self-Care Portal.

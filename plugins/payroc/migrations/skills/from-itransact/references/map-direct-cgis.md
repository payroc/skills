# iTransact → Payroc: direct-call CGIs, the captcha interstitial, card registration and merchant registration

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the iTransact direct-call
> CGIs (void, credit, postauth, trancred, tranforce, tranretry) and three public CGIs that take no login
> session (the captcha interstitial, the card registration form and the merchant registration
> form) to what Payroc offers instead. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-10-11. Read mappings from this file, not from memory —
> a plausible-sounding mapping that isn't here will look correct in review and fail in production.

```text
IN:  The direct-call CGIs: CGI void/void.cgi, credit/credit.cgi, postauth/postauth.cgi, trancred/trancred.cgi,
     tranforce/tranforce.cgi, tranretry/tranretry.cgi (form posts with mid and pwd, or a logged-in
     session). Three public CGIs that take no login session: CGI captcha/captcha.cgi (the reCAPTCHA
     interstitial that ord.cgi posts to), CGI ma/ccreg/ccreg.cgi (a card registration form keyed by an account id)
     and CGI mreg/mreg.cgi (a merchant registration form that needs a reseller id and posts the result to
     a caller-supplied return address).
OUT: The xmltrans2 follow-on operations (VoidTransaction, TranCredTransaction, PostAuthTransaction,
     TranForceTransaction, TranRetryTransaction): map-xml-api.md. The Melia follow-ons (PATCH
     /transactions/:id/void, /capture, /credit): map-json-api.md. The ord.cgi order post that
     captcha.cgi serves: map-browser-forms-and-pages.md. The other no-session CGIs, which
     no-equivalent-register.md lists. The Control Panel pages that post to these CGIs in session
     mode (a human using an iTransact UI, not an integration). Authentication, outcome signalling,
     duplicate control and amounts: map-protocol-auth-and-results.md. Identifiers:
     identifier-translation.md.
ADJACENT: map-xml-api.md holds the XML equivalents of void, credit, postauth, force and retry;
     map-browser-forms-and-pages.md holds ord.cgi (the caller of captcha.cgi) and the split form;
     map-json-api.md holds the Melia void, capture and credit routes; map-protocol-auth-and-results.md holds
     the URL table that routes your URL to these keys; map-gateway-servlet.md holds the
     `SERVLET MerchantRegistrationRequest` row (the gateway-side registration of an acquirer account),
     which `mreg.cgi`'s Payroc boarding target shares. If your call is not in the table below, it
     is not absent from iTransact -- check the sibling, then SKILL.md's routing table, then check what your code sends.
```

## Cross-cutting facts

Authentication, outcome signalling, duplicate control, amounts and currency, and the URL spellings are stated once in [`map-protocol-auth-and-results.md`](map-protocol-auth-and-results.md): see its `AUTH S5 direct-call CGIs` row, `TRANSPORT HTML form post: direct-call CGIs (S5)`, `TRANSPORT duplicate control: direct-call CGIs (S5)`, `TRANSPORT amounts: direct-call CGI total (S5)` and the `URL` table rows for these keys. Identifier moves (`id` and `xid` to `paymentId` or `refundId`, `mid` to `processingTerminalId`) are in [`identifier-translation.md`](identifier-translation.md): see its `FIELD xid` row for the direct CGIs and `FIELD mid`. Facts local to this file:

1. **Deployment of the six direct-call CGIs and `ccreg.cgi` is not established.** None of them is in any tagged iTransact release image since December 2021. That says nothing about what production runs: an untagged build is not ruled out, and whether production still serves these CGIs is not established. Their rows are `unverified` on that half, and **callers are to be migrated either way**. `captcha.cgi` is different: it is part of iTransact's current release and is served directly.
2. **The six direct-call CGIs serve two kinds of caller from one URL.** With `mid` and `pwd` present a request is an integration; otherwise it needs a login session and is the Control Panel's transaction-detail page (a human). Only the `mid` and `pwd` branch is mapped here. A Control Panel user moves to the Payroc Self-Care Portal; that is not an API migration.
3. **Every direct-CGI follow-on needs a Payroc `paymentId`, and an iTransact xid is not one.** No Payroc operation accepts an iTransact xid (identifier-translation.md fact 1), so a void, capture, refund, force or retry of a transaction that was created on iTransact cannot be run on Payroc after cutover. See the `FIELD xid` historical `none` row in identifier-translation.md for the alternative (finish follow-ons while iTransact runs; it is being retired, map-protocol-auth-and-results.md fact 8).
4. **A follow-on creates a new iTransact transaction; Payroc hands back the payment.** Each CGI takes the original transaction's xid, creates the follow-on, and returns the follow-on's new xid in `lookup` (identifier-translation.md fact 3). Code that stores the child xid must store the Payroc `refundId` (a refund) or keep the `paymentId` (a reversal or capture).
5. **Confirmation emails, the success redirect and the postback are CGI behaviours with no Payroc API counterpart.** Each of these CGIs always emails the merchant an "ok" letter, emails the customer when the merchant's confirmation setting is 1, and then either redirects to a configured URL (or `template_code` template) or, with `ret_mode=post`, posts a signed set of `lookup` and `passback` pairs (and `save` values for five of the six) to `ret_addr`. On Payroc the caller reads the JSON response (map-protocol-auth-and-results.md RESULT rows). Payroc's operation documentation does not say whether Payroc sends a cardholder or merchant email on these operations, so confirm with your Payroc implementation contact before dropping a letter a merchant relied on.
6. **iTransact scopes several of these checks more loosely than Payroc does.** An integration that relied on that looser scoping will not behave the same after the port (inferred; test it). On Payroc a follow-on is scoped by the caller's credentials and the `paymentId`. This is a behaviour change only.
7. **Payroc follow-on operation texts.** `reversePayment` is documented for "a payment in an open batch" and `refundPayment` for "a payment that is in a closed batch", and `refundPayment` on an open-batch payment reverses it. A payment response lists the follow-ons it supports (`capture`, `refund`, `fullyReverse`, `partiallyReverse`, `incrementAuthorization`); read it instead of guessing the batch state.

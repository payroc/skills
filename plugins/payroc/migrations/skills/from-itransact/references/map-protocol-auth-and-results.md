## Cross-cutting facts

**Row keys.** Rows that are not a single iTransact call (`TRANSPORT`, `AUTH`, `RESULT`, `HOST`, `DATA` here, and `FIELD` in identifier-translation.md) carry a surface code so other files can cite them. The codes are labels only: S1 xmltrans2 XML API; S2 deprecated xmltrans `SaleRequest`; S3 order form (`ord.cgi`); S4 split and buy-now forms; S5 direct-call CGIs; S6 recurring billing; S7 postbacks; S8 transaction listing and pinauth; S9 the JSON API on api.itransact.com; S10 payouts_api; S11 the merchant JSON API under `/h/merchant_api`; S12 Checkout script; S13 gateway servlet; S14 official SDKs; S15 plugins and clients; S16 nvpairs; S17 hosted payment pages; S18 receipt page; S19 integration settings.

Stated once here; every other file points back to this section instead of repeating it.

1. **Payroc is JSON over HTTPS with a bearer token; iTransact is five different protocols.** iTransact speaks XML over HTTPS POST (S1, S2, S13), HTML form posts (S3, S4, S5), JSON REST (S9, S10, S11), a browser script (S12), listing URLs and a SOAP service (S8). Payroc declares one security scheme, `bearerAuth` (`type: http`, `scheme: bearer`, `bearerFormat: JWT`), with the server `https://api.payroc.com/v1`, used for test and live alike (the API key decides which). The token comes from the Identity Service: `POST https://identity.payroc.com/authorize` (also the same host for test and live) with an `x-api-key` header, one hour expiry. That endpoint has no `operationId` in Payroc's API specification; the SDK method is `auth.retrieveToken`. Payroc's API documentation describes no other identity or token endpoint. The token exchange (endpoint, header and response) is in [`identity-call.md`](identity-call.md). Payroc's only non-JSON request body in its published API specification is one `multipart/form-data` boarding upload (`createProcessingAccountAttachment`); its API documentation describes no XML, SOAP, form-encoded or script transport for taking payments.
2. **Authentication: nine iTransact schemes, none of them a bearer token, none ported.** S1 signs the literal first `<Op>` to first `</Op>` text with HMAC-SHA1; S2 sends a vendor password in the body; S5 sends `mid` plus a hashed `pwd` and needs an IP filter; S8 signs 44 named parameters (paging unsigned); S9 signs the raw body with HMAC-SHA256; S11 signs sorted `name=value` pairs with HMAC-SHA1; the S6 transparent billing update uses a signed link; S12 sends a credential from the browser; S13 takes username and password or a client certificate. Payroc's documentation describes **no request signing and no IP allow-list** for the REST API (not a confirmed absence); the Hosted Payment Page is the exception: its load request carries a SHA-512 `HASH` built with a terminal secret, and its receipt returns one to verify. Secrets move from per-request signatures and merchant passwords to one API key that is exchanged for a one-hour token.
3. **The S1 signature covers literal text, so a re-serialising proxy breaks it.** The server takes the substring from the first `<Op>` through the first `</Op>` of the request text as received, matched as literal tags. Relevant to any dual-running or proxying period before cutover. The Payroc REST API has no equivalent signing, so the answer there is to remove the signing code, not port it (a form post moved to the Hosted Payment Page must build and verify its `HASH`, fact 2).
4. **Outcome signalling differs on every surface, and differs again on Payroc.** S1 and S2 answer HTTP 200 with a `Status` and `ErrorCategory` in the XML body; S3 returns either an error page or a posted `err`/`die` pair, or signed `lookup` pairs; S9 answers 402 on a decline; S13 returns a response root in the body with HTTP 200 for application errors. Payroc `payment` returns **201 whether the card is approved or declined**; read `transactionResult.status` and `responseCode`. No Payroc response declares 402 (Payroc's API specification and documentation mention none).
5. **iTransact's production decline and error texts are not established.** Test what your integration receives. Do not map a text; map the status.
6. **Duplicate control inverts.** Only `ord.cgi` (and so, probably, the split form) has one, and it is an opt-in merchant setting that rejects a content match; iTransact is not known to have one on any other surface. Payroc's `Idempotency-Key` is a required UUID v4 header that replays a saved response for the same key, URI and body (the saved response is kept for seven days). See the duplicate rows.
7. **Amounts are not one format.** XML, form and CGI surfaces take decimal dollars; Melia and payouts take integer cents; the servlet takes either. Payroc `order.amount` is an integer in the currency's lowest denomination, with a required `currency`. No iTransact surface carries a currency field (see the currency row). See the amount rows.
8. **Payroc is retiring the iTransact gateway, so the migration is time-critical.** See the DATA rows.
9. **Open points that apply to the rows below.** S13 (the gateway servlet) is **in, provisional**: which integrations still call it directly is not established. The S5 direct-call CGIs are in iTransact's code but not in any tagged iTransact release image since December 2021; that is a statement about image builds, not about production. Whether production still serves them is not established, and callers should be migrated either way. payouts_api is not routed per iTransact's routing configuration, and whether another host serves it is not established. Split-form card results are probably `ord.cgi` results.
10. **How to tell whether a payment is still in an open batch.** Decide an `IF:` about an open or closed batch from the payment you read back, by payment type. Card payment (`getPayment`): `supportedOperations` lists `fullyReverse` while a full reversal is possible (map-direct-cgis.md fact 7); `transactionResult.status` `ready` and `pending` are described as in the open batch, and `complete` as funds moved. Bank-transfer payment (`getBankTransferPayment`): Payroc declares no `supportedOperations` on it, so use `transactionResult.status` (`ready` and `pending` described as in the open batch, `complete` as funds moved). Whether a status changes when the batch closes, rather than when funds move, is not stated (inferred; test it in the test environment). Never pick the arm by sending one and reading its error.

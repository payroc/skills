# IBX → Payroc: card transactions — `transact` / `transact2`

> **Local snapshot — authoritative for this skill.** Payroc's own operation-by-operation mapping from
> the IBX `transact` and `transact2` SOAP services to the Payroc API, covering `ProcessCreditCard`,
> `ProcessSignature` and `EmailReceipt`. Per-row confidence is carried in the `C` column; the legend
> is in [`_sources.md`](./_sources.md). Last synced: 2026-09-14. Read mappings from this file, not
> from memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

     EmailReceipt only.

     equivalents -- map-rest-transactions.md and map-token-payments.md.
ADJACENT: map-extdata-tags.md covers the ten ExtData tags IBX accepts and documents
     nowhere. NINE of the ten reach the credit-card path, and four change how the

     surface as harmless.
     map-batch-and-settlement.md holds a DIFFERENT CaptureAll hazard from this file's

This file owns the delta; those skills own the request schema.

## Cross-cutting facts

Stated once here; see `identifier-translation.md` for the full detail.

- **Currency cannot come from your IBX request.** IBX has no currency field on any API surface, and
  Payroc's `order.currency` is required. It resolves from processor or terminal configuration, or from
  an intake question. There is no field to read it from on the legacy side, ever.
- **The `DDDDD.CC` amount format is not what the SOAP validator enforces — but do not read that as
  permission to send more.** The validator checks only two decimal places, digits before the point,
  and a total length of no more than twelve characters, with no five-digit check. So **for intake,
  assume legacy rows above `99999.99` may exist** and do not build validation that rejects them.
  **For what you send, `99999.99` is the recommended ceiling:** IBX's REST surface declares its card
  amount as a single-precision float, which turns `999999.99` into `1000000.00`, so `99999.99` is the
  last value that round-trips cleanly — exactly the documented figure. Above it the REST failure mode
  is **silent rounding, not an error.** If you process larger amounts today, ask your Payroc
  implementation contact what the real ceiling is and which layer imposes it. See
  `identifier-translation.md`.
- **The two-decimal rule *is* enforced, so conversion to minor units is exact** — no rounding
  ambiguity. But convert by ×100 **only for two-decimal currencies.** Payroc's `order.amount` is in
  the currency's lowest denomination and its currency enum includes zero-decimal (`JPY`, `KRW`) and
  three-decimal (`BHD`, `KWD`) entries. Since currency resolves from configuration rather than from
  the request, confirm the terminal's currency before applying ×100 — otherwise the error is 100×.
- **Card expiry is `MMYY` on both platforms** — no digit-pair conversion in either direction. But
  Payroc's four-digit pattern does not range-check the month, so `9999` passes schema validation and
  is only ever rejected by the issuer, if at all. **Range-check the month yourself before sending.**
  Separately, IBX's own runtime caps the expiry year at 39, so a card expiring in 2040 or later cannot
  be represented in IBX at all — you may already be hitting that ceiling.
- **`PNRef` lives in your database, never IBX's.** A pre-migration `PNRef` has no Payroc `paymentId`.
  The bridge is `order.orderId` on the way in (≤24 characters; uniqueness is stated in prose, not
  enforced) and `listPayments?orderId=` on the way back out — handle both zero matches and more
  than one.
- **A success result is not "money moved" for every row below.** Check the rows tagged `SEMANTIC:`.

## `ProcessSignature`

Two rows, split by reference-resolution behaviour. **Note that the format split runs differently** —
coordinate arrays, base64 rasters and a TIFF document are distributed across both tiers. The two
partitions are not the same and must not be merged.

`SCOPE:` IBX applies no sanitisation, no decode and no length check to any `ProcessSignature`
parameter — signature data is appended into the outbound payload raw. Payroc's contract is capped and
alphanumeric-only, so **do not assume existing stored signature data will pass.**

| IBX call | V | Payroc target | Request delta | Behaviour change | C |
|---|---|---|---|---|---|
| `SOAP transact.ProcessSignature {SignatureType=SIGNATURE1,SIGNATURE2}` | partial | `adjustPayment` with `adjustments[].type: signature`, `cardholderSignature` | `+type: signature`; `SignatureType` has no target field at all and is dropped; **`SignatureData` here is a coordinate re-encode, NOT a raster conversion** | `LOSS:` IBX's own published documentation is explicit: base64 encoded image data applies to the Hypercom Legacy and Enhanced formats, and **for all other signature types the field is an array of coordinates** in the form `x1,y1^x2,y2^…^~`, using `0,65535` for any pen-up event. `SIGNATURE1`/`SIGNATURE2` are Lipman credit and check — "all other signature types" — so **this tier is already coordinates and needs no image processing.** The real work is a re-encode: split on `^`, drop the `~` terminator, map the pen-up sentinel `0,65535` to Payroc's `0000`, scale to Payroc's 300×100 canvas with the y-axis measured from the top, convert each value to **base-28**, concatenate, and strip punctuation to leave alphanumerics only — keeping the result **under** 1600 characters by reducing the sampling rate if needed. **IBX's own canvas dimensions and y-axis origin are not documented anywhere, so the scaling factor is an open question** — escalate rather than assuming 300×100. `SEMANTIC:` one-shot — `adjustPayment` rejects a later change once a signature is set. | verified (both platforms' formats) / unverified (the IBX→Payroc canvas scaling factor) |
| `SOAP transact.ProcessSignature {SignatureType=SIGNATURE3,SIGNATURE4,HYPERCOM_LEGACY,HYPERCOM_ENHANCED,CHECK,RECEIPT1}` | partial | same target as above | **This tier is not one format.** `HYPERCOM_LEGACY`/`HYPERCOM_ENHANCED` are **base64 raster images** — for these two only, raster-to-vector extraction is real engineering work rather than a field remap. `SIGNATURE3`/`SIGNATURE4`/`CHECK` are coordinate arrays, so the re-encode in the row above applies. `RECEIPT1` is a TIFF **document**, not a signature, and probably not `cardholderSignature`'s business at all. **`PNRef` is a conditional here, not a requirement.** | `SCOPE:` when `PNRef` is empty there is **no rejection** — the whole block, quota check included, is skipped and processing continues. Do not expect a call without `PNRef` to fail. When `PNRef` *is* supplied and matches, the stored result and approval code **overwrite** the caller's arguments — except for cash, where they do not. `SEMANTIC:` the image quota has **two** caps, not one: an unconditional total per transaction, checked *before* a per-component limit that allows one image but two signatures. **A call can therefore fail on the aggregate cap while still under the signature limit.** Note also that IBX's published documentation lists only five of these six values — it omits `CHECK` entirely. | verified (the behaviour above) / unverified (**the numeric limits themselves**; and whether `RECEIPT1` and `CHECK` count as an image or as a signature is unsettled. **If `RECEIPT1` counts as an image its limit is one, not two — do not quote a flat "max two per transaction" across all six values**) |

## `EmailReceipt`

| IBX call | V | Payroc target | Request delta | Behaviour change | C |
|---|---|---|---|---|---|
| `SOAP transact.EmailReceipt` | none on the API side, with **one open configuration question — see `CFG:`** | `—` | n/a. The real signature is four fields: `UserName`, `Password`, `PNRef`, `EmailAddress`. **Ignore IBX's published *prose* for this call** — it borrows `ProcessCreditCard`'s description and lists `TransType`, `CardNum`, `ExpDate`, `Amount` and FSA/HRA fields this operation does not accept. The WSDL's own schema declares exactly those four elements and is correct. | `SEMANTIC:` a success result means **"row queued", never "sent."** Delivery is a separate out-of-process service that runs roughly every 90 seconds. **`LOSS:` no Payroc operation, webhook or subscribable event emails a cardholder a receipt for a completed payment.** You can check that absence yourself against the public documentation: the payment resource exposes only adjust, capture, refund and reverse; the only two email-sending operations in the API are merchant-facing pricing reminders and sharing a payment link, which emails a request *before* payment; and every subscribable event is a boarding event delivered over a webhook, which cannot email anyone. `CFG:` **but do not conclude there is no Payroc-side facility at all.** A boarding-time terminal flag exists — `receiptNotifications.emailReceipt`, *"indicates if the terminal can send receipts by email"*. It is set once in the terminal order and is read-only afterwards, and it is **not** POS-hardware-only: the gateway and web solution templates accept it, and a processing terminal is defined as a physical **or virtual** terminal. **Whether it fires for a payment submitted through the API is not documented and cannot be determined from the specification.** So the answer is: **build receipt emailing, and turn it off only after a test payment submitted through the API with a cardholder email on the payment, on the terminal profile you will run in production, shows that the flag sends a receipt.** A UAT terminal's configuration does not tell you what the production one does. Wrong in that direction costs a duplicate receipt, which someone notices. Skipping the build on an assurance that turns out to be wrong means cardholders quietly stop getting receipts. | verified (the IBX behaviour, and the API-side absence) / **unverified** (what `receiptNotifications.emailReceipt` actually triggers — the test payment above settles it for the terminal profile it ran on, and only that one) |

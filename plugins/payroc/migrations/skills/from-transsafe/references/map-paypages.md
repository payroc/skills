# TranSafe → Payroc: pay pages — PaymentFrame iFrame, TicketRequest, hosted and invoice pages

> **Local snapshot — authoritative for this skill.** Payroc's own mapping from the TranSafe PaymentFrame
> iFrame, the bare TicketRequest POST, Hosted Paypage actions, the customer-facing hosted page and the
> invoice page to the Payroc API. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

## Cross-cutting facts

1. **Stated elsewhere, not repeated per row.** map-protocol-auth-and-results.md: KV → HTTPS + Bearer from the Payroc identity service; the POST/HMAC transport accepts only `TICKETREQUEST`, `ADMINCARDSHIELDTICKET` and `ALTPAYMENTINIT` and routes the first two here; outcome signalling (Payroc returns **201 on approval and on decline**; read `transactionResult.status`); `duplcheck` → `Idempotency-Key`; decimal-string amounts → integer minor units, `+order.currency`. identifier-translation.md: `FIELD cardshieldticket` (ticket → `singleUseToken`; 300 s and reusable → 30 min and one use; never validate its length; profile-bound); `profile_id` → `processingTerminalId` (assigned at boarding). map-card-transactions.md: every operation that takes `cardshieldticket` has its own row there (`POST /transaction/purchase`, `/preauth`, `/verify`, `/refund`, `/cardtype`, gift, EBT, card lists); this file maps only how the ticket is **minted** and what replaces that. map-tokens-vault-and-customers.md: a ticket sent to `POST /vault/account` (`token_add`) → `createSecureToken` with source `singleUseToken`.
2. **Three page types, three Payroc targets: PaymentFrame goes to Hosted Fields (not finally decided); hosted and invoice pages go to payment links or the Hosted Payment Page.** PaymentFrame and the bare TicketRequest → **Hosted Fields**. Payroc's position is that a PaymentFrame integrator must re-integrate to Hosted Fields before its merchants cut over, with no auto-migration possible. That position is the latest but is not finally decided; confirm it with your implementation contact before you commit to the work. Hosted paypage → a **multi-use payment link** or the **Hosted Payment Page (HPP)**; invoice page → a **single-use payment link**. Payroc names its Hosted Payment Page and Payment Links as the replacement for these pages but has not said which page type takes which target, so treat the link-versus-HPP choice, and single-use links for invoices, as a recommendation, not a Payroc decision; confirm it with your implementation contact. Every hosted/invoice row therefore carries the target as `inferred`.
3. **Ticket vs Payroc tokens (behaviour, not shape).** A `cardshieldticket` is not a single-use token.

   | | TranSafe `cardshieldticket` | Payroc Hosted Fields |
   |---|---|---|
   | Browser credential | none; the page carries a server-computed HMAC valid ±15 min | session token from `createSession`, **10 min**, one per page load |
   | Result of the form | ticket, 9–10 digits, **300 s**, **reusable**, bound to the profile | single-use token (exactly 128 characters), **30 min**, **one use** |
   | Carries | card or ACH fields incl. CVV, street/zip, 3DS results, `ordernum`, `custref`, descriptors | payment details only; order, address and 3DS data go on the `payment` call |
   | Amount | not bound (set on the charge) | not bound (set on the charge; the 3DS MPI call takes an amount) |
   | Charge | merchant server sends `cardshieldticket` on any operation that accepts it | merchant server sends `paymentMethod.type: singleUseToken` on `payment` / `bankTransferPayment` |

4. **Credentials.** TranSafe signs the frame config with an API-key secret or a user password; the browser never sees it. Payroc Hosted Fields uses the API key → Bearer (server) → session token (browser). Payroc's HPP, by contrast, is authenticated by a merchant-computed SHA-512 `HASH` keyed by a **terminal secret** set in the Self-Care Portal: structurally the closest thing to TranSafe's local signing, but it is a full-page redirect, not embedded fields. Do not confuse the terminal secret with the API key.
5. **The migration path from PaymentFrame to Hosted Fields.**
   1. **Inventory** what you have: which pages load the PaymentFrame iframe; any use of the bare ticket POST; ticket reuse; 3DS, PayPal, ACH and gift BIN use in the frame. A merchant stays on TranSafe until its integration passes step 7.
   2. **Provision**: an identity-service API key per environment (for testing, create a test API key in the Developer Portal; request a live key from Payroc Integrations). Whether one key covers every merchant's `processingTerminalId` is not documented (tokens carry a `scope`) **[unverified]**: confirm key-to-terminal scoping with Payroc Integrations; per merchant a `processingTerminalId` (existing merchants: from your implementation contact); terminal enablement for ACH, 3-D Secure (sign-up plus an MPI receipt URL) and secure tokens if cards are saved (Config, PayPal/ACH and 3DS rows). Confirm ACH readiness with your implementation contact before mapping an ACH frame.
   3. **Server: replace HMAC config signing** with identity call → `createSession` (`scenario`, `libVersion`) on every page load (Config row).
   4. **Page: replace the iframe** and `PaymentFrame.js` with the Payroc CDN script (SRI hash, version = `libVersion`), one container per field, your own labels and address/zip fields, `styles` (Embed and Options rows). Fix the page CSP (CSP row).
   5. **Client events:** `paymentSubmitted` → `submissionSuccess {token, expiresAt}`; simulated `DENY` with `DATA_ACCOUNT` (Luhn) → expect `fieldValidityChange` (documented for format errors only; Luhn behaviour and timing to be tested in the test environment, step 7), with an `error`/decline fallback; simulated `DENY` with `SETUP_CARDTYPE` (BIN not in the profile's ranges) → no client event, handle it as a decline on `payment`; failures → `error`; drop `height`/`reload`; replace an external submit button (client JS rows).
   6. **Server charge:** `cardshieldticket` → `paymentMethod.type: singleUseToken` on `payment` (card) or `bankTransferPayment` (ACH); if one ticket fed several calls, tokenize once (`payment` with `credentialOnFile.tokenize: true` (optionally your own `secureTokenId`; the gateway generates one if omitted), or `createSecureToken` with source `singleUseToken`) and send the secure token on every later call; drop a pre-sale verify, because `verifyCard` takes card details only, not a single-use token; ACH reuse tokenizes on `bankTransferPayment`; add the MPI step if 3DS is used; branch on `transactionResult.status` (Charge and 3DS rows; map-protocol-auth-and-results.md).
   7. **Test in the test environment** before any merchant moves: fields render; a Luhn-invalid number (record whether `fieldValidityChange`, `error` or a decline results); an approval and a decline (both HTTP 201); a second use of a token fails; submit a form initialised more than 10 minutes earlier and record the event or error raised (what an expired session reports is undocumented; there is no expiry event, but the session-token response also returns `expiresAt`, so a renewal timer can key off it); ACH and 3DS paths if used; the CSP admits the CDN in the test environment and production.
   8. **Cut over per merchant**, page and server together: a TranSafe ticket cannot be redeemed on Payroc or vice versa, so there is no carry-over of in-flight tickets (both expire within minutes).
6. **Absences in Payroc's public docs and API reference** (each restated in its row): Payroc's public docs and API reference describe no PayPal support and no captcha or carding-defence feature; Hosted Fields has no domain registration or allow-list; Hosted Fields documents three events only (`submissionSuccess`, `error`, `fieldValidityChange`); the payment-links API has no `redirect`/`returnUrl`, attachment, PDF or line-item field, and its sharing method enum is `email` only.
7. **Apple Pay and Google Pay are additions, not mappings.** The TranSafe frame has no wallet support. Payroc offers them as separate integrations (integrate-apple-pay, integrate-google-pay). Apple Pay needs terminal enablement by Payroc and per-merchant domain registration in the Self-Care Portal; Google Pay documents no Payroc domain registration or Self-Care step, but it does have a go-live step: register the integration and website with Google, then contact Payroc's Integrations Team. Offer them after the migration path above is done; they are not part of it.

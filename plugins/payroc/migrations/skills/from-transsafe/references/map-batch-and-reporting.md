> the TranSafe batch, transaction-report, chart-data, device-report, usage-report and public System
> Scheduler (automated settlement) actions (REST v2 / KVS v9) to the Payroc API. Per-row confidence is
> carried in the `C` column; the legend is in [`_sources.md`](./_sources.md). Last synced: 2026-11-03.

## Cross-cutting facts

Stated elsewhere, not repeated per row. [map-protocol-auth-and-results.md](map-protocol-auth-and-results.md): KV → HTTPS + Bearer; a TranSafe report returns the **whole** result in one response (CSV on KV, a JSON `report` array on REST) while Payroc lists page with `limit` (max 100) and `after`/`before` (`TRANSPORT report output` row); `Idempotency-Key` is required on `closeBatch`; amounts are decimal strings on TranSafe and integer minor units on Payroc. [identifier-translation.md](identifier-translation.md): `FIELD batch` (TranSafe's per-route sequential batch number ≠ Payroc's gateway-assigned `batchId`; a Payroc payment carries no batch number), `FIELD profile_id` (→ `processingTerminalId`, assigned by Payroc at boarding; ask your implementation contact how your TranSafe profiles map to Payroc terminals before porting any call that takes `profile_id`), `FIELD formatted time params` (TranSafe relative dates and merchant-time-zone formats → ISO 8601), `FIELD ttid` (open TranSafe preauths and the last TranSafe batch are drained **on TranSafe** before cutover). File-local facts:

1. **The TranSafe batch model.** Batches are per merchant profile **and per settlement route** (`route_id`); only one batch per route is open at a time. A sale (or a completed preauth) joins the open batch; an uncaptured preauth or a `capture=no` sale joins none until it is completed or captured. A batch is **open** → optionally **closed** (`batch_close`: the counter rotates, the batch stays unsent) → **settled** (`settle`: submitted to the processor). `report_totals=unsettled` labels each unsettled batch `open` or `closed`. Rescind, clear, renumber and resequence edit that local state; TranSafe's own documentation reserves the advanced ones for use "only after consultation, and confirmation with the processor". Processors that assign batch numbers themselves make close and resequence fail ("processing institution manages batches, not setting locally"); TranSafe's renumber does not make this check.
2. **Payroc `closeBatch` is TranSafe's *settle*, not TranSafe's *close*.** `POST /processing-terminals/{processingTerminalId}/close-batch` takes no body and no batch number, needs an `Idempotency-Key`, and returns **`202`** with `cutOffTime` (`HH:mm`) and `timezone`: "a cut-off time that indicates when our gateway closes the batch", not a settlement result. Closing **is** submitting on Payroc: "To settle a payment, the terminal must first close the batch and then our gateway settles the payments within an hour"; Payroc's own workflow "Close a terminal batch" is summarised as "Manually close (settle) the current batch". Payroc has no closed-but-unsettled state and no way to pick a batch. **No task skill covers `closeBatch`:** order-a-terminal lists it as "out of scope for this skill".
3. **Payroc settlement reporting shows submitted (settled) batches only.** `getbatches` returns batches "that your merchants submitted to the processor on a specific date" and requires `date`; `getTransactions` and `getAuthorizations` require `date` (the batch submission date) or `batchId`. None of them offers an open-batch view. **What is still open** is visible only per transaction: `listPayments` and `listRefunds` take `settlementState` (`settled` or `unsettled`) and `settlementDate`. `listPayments` is covered by run-a-card-sale (including `settlementState`) and `listRefunds` by refund-a-card-payment. ACH-enabled merchants also need the bank-transfer payment and refund lists, which take `settlementState` too → take-an-ach-payment, refund-an-ach-payment. Outside the API, the Self-Care Portal shows "real-time transaction data in open batches". Settled data: view-settlement-batches, view-settled-transactions, view-authorizations.
4. **Automated settlement moves from a TranSafe API to Payroc terminal configuration.** TranSafe: a `SETTLE` scheduler task per profile, schedule `HHMM\|<days>` (`sun;…;sat`), `HHMM\|*` (daily) or `HHMM\|<day of month>`, evaluated in the **profile's** time zone. Each run pulls the unsettled-totals report and settles **every open and closed batch on every route** of the profile, continuing past failures, then emails a SUCCESS / FAIL / MIXED / NO OPEN BATCHES summary to the merchant's notify address, subject to the server's mail settings. TranSafe's documentation recommends automatic over manual settlement. Payroc: each processing terminal carries `batchClosure` = `automatic` (+ `batchCloseTime`; closes "at a specific time each day") or `manual`, set when the terminal is ordered (`createTerminalOrder` `solutionSetup.batchClosure` → order-a-terminal). The docs say "To adjust when the terminal closes a batch, use the terminal settings in the Merchant Portal"; no Payroc API operation updates a processing terminal or a terminal order after creation, and none schedules anything.
5. **TranSafe report semantics to carry over.** `bdate`/`edate` accept relative strings and are read in the merchant's time zone. Reports with `COMPLETE` or `DECLINED` and no `bdate`, `edate`, `last_modified_*`, `ttid`, `ordernum` or `batch` **silently default to the last 30 days**. `COMPLETE` means "settled or voided", and voids are included unless `showvoids` is false (`only` = voids only). TranSafe returns payments **and** returns in one report; Payroc splits them across `listPayments` and `listRefunds`.
6. **History does not move.** Payroc reporting covers transactions Payroc processed; the Payroc API has no import, upload or migrate operation for transaction, batch or chart history **[inferred]**. TranSafe also overwrites a settled batch's data when its batch number is reused, and keeps the device journal for 30 days only. See the DATA rows.
7. **What the Payroc API does not have** (stated so you can check it against the public API reference):
   - Batch operations are `closeBatch`, `getbatches` and `getbatch` only: no unsettle, force-settle, renumber or batch-number write.
   - Processing terminals and terminal orders have no update or delete operation: they cannot be changed through the API after creation. No operation in the batch, transaction or processing-terminal resources schedules anything.
   - No aggregate or chart operation. The only "breakdown" fields are itemised order breakdowns and the ACH-deposit breakdown of sales, returns and fees. The only report-like operation is the disputes-statuses one.
   - No usage report and no device journal.
   - No open-batch or unsettled view in the batch, transaction or authorization operations (fact 3).
   - No import operation (fact 6).

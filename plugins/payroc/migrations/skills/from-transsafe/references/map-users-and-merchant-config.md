## Cross-cutting facts

Transport, authentication mechanisms (Basic, API-key headers, MFA code, dual control), outcome signalling, `Idempotency-Key` and pagination are in [map-protocol-auth-and-results.md](map-protocol-auth-and-results.md) (its cross-cutting facts and Authentication rows). This file maps the **management** actions behind those credentials; it does not repeat how they are sent. `profile_id` and `group_id` are in [identifier-translation.md](identifier-translation.md). Group hierarchy and permissions are in [map-boarding.md](map-boarding.md). File-local facts:

1. **Payroc has no user, credential, permission, fraud-rule, card-list or key-management API.**
   - **Operations.** No Payroc operation concerns users, API keys, MFA, passwords, security questions, velocity, deny or allow lists, fraud rules, P2PE, BDKs, encryption keys, permissions, roles or limits. The only operations whose names touch these topics are the five secure-token operations (`createSecureToken`, `getSecureToken`, `listSecureTokens`, `updateSecureToken`, `deleteSecureToken`; these are payment tokens, see map-tokens-vault-and-customers.md) and two read-only device operations (`searchDevices`, `retrieveDeviceConfiguration`).
   - **Documentation.** Payroc's public documentation does not describe a velocity rule, deny list, allow list, key injection or BDK, security-question or password reset, account lockout or unlock, stand-in key, or multi-factor enrolment. Payroc's documentation mentions P2PE and E2EE only in general descriptions, not as an operation or setting; the API-level fraud controls are 3-D Secure, AVS and CVV.
   - **Task skills.** None of the Payroc task skills covers API keys, users, MFA, velocity, card lists or device keys. `integrate-payroc-cloud` does not configure or pair devices.
2. **API keys: TranSafe mints them through the API; Payroc issues them outside it.** TranSafe: `user`, `profile` or `group` keys, a public id plus a secret, created by a **Basic-authenticated** call, up to 100 per owner, each with its own subset of the owner's permissions, an optional expiry with `EXTEND_ON_USE`; the secret is returned once (`apikey_secret`), expired keys are purged by a background job, and a user's keys are deleted with the user. Payroc has two kinds of key. The **API key** used with the identity service: "We send you an API key when you sign up with us"; for testing, create a test API key in the Payroc Developer Portal (https://developers.payroc.com); developers cannot self-serve live API keys and must contact the Payroc Integrations team. The **Payroc App API key** is specific to a merchant account and its processing terminals and is created, viewed, edited (alias, notification email, per-API permissions for the Account, Customer, Transaction, Bank Transfer and Reporting APIs, processing-terminal scope), revoked and reactivated in the **Self-Care Portal**. It is documented for the Payroc App and the Payroc Cloud Simulator; **whether the identity service accepts it for REST API calls is not stated in Payroc's documentation** (unverified); confirm with your implementation contact before relying on one. Consequence: TranSafe's recommended web/mobile pattern, have the user log in with a username and password, then request an API key representing the user with `EXTEND_ON_USE`, cannot be ported. A Payroc API key is a server-side secret: do not use API keys in publicly accessible areas, for example client-side code.
3. **TranSafe users are API principals; Payroc users are portal accounts.** Every Basic-authenticated TranSafe call runs as a user. Users sit in a group and carry four permission sets and flags (`UNATTENDED` "Integration account only", `SELFVIEWONLY`, `RESET_PEER_PASSWD`, `MFA`, `ALLOW_UNLINKED_REFUND`, `ALLOW_GROUP_APIKEYS`), a default profile and an optional lock to one profile. The Payroc API has no user principal: the Bearer token stands for the API key (map-protocol-auth-and-results.md). Payroc portal users exist (Self-Care Portal sign-in with a password; if you don't have credentials for the Self-Care Portal, contact the Payroc Integrations team), but Payroc has not published how portal users are created or how TranSafe permissions map to Payroc roles; agree the mapping with your implementation contact before cutover. Payroc states that it handles user account creation and role mapping on the Payroc Gateway and that every TranSafe portal user needs active login credentials on the Payroc Gateway before cutover, but this is not in Payroc's published documentation; confirm it with your implementation contact. So: **people become Payroc portal accounts through Payroc (`config`); integration (`UNATTENDED`) users become Payroc API keys.** Payroc moves existing merchants; confirm with your implementation contact that your portal users move with them.
4. **MFA, security questions and self-service resets protect TranSafe passwords; Payroc API credentials have no password.** The MFA call "requires the full username and password, an APIKey cannot be used to call this function"; password self-reset can be called without API credentials and is driven by username, an emailed or SMS code and three security answers. No Payroc operation or document covers any of it. Portal-login security on Payroc is Payroc's and is not documented: escalate to Payroc Integrations. MFA enforcement (from TranSafe 10.18.0) and MFA cookies depend on your TranSafe release; check which release you run against.
5. **Velocity rules and the deny list decline before the card goes online, with their own codes.** TranSafe velocity rules are hierarchical (group rules apply to every profile below; groups or profiles may override, optionally only upward), metered by card type, `DECLINE`, `UNLINKED_REFUND` or `TRANSACTION_AMOUNT`, in `COUNT`, `SALE_AMOUNT` or `REFUND_AMOUNT`, over one transaction, 15–90 minutes, 1–23 hours or 1–31 days; they block by default or only alert. A blocked transaction ends as `code=DENY`, `msoft_code=VELOCITYTHRESHOLD`, "Velocity rule threshold exceeded"; a deny-list hit as `code=DENY`, `msoft_code=CARDDENYLIST`, "On card deny list"; on REST v2 both are HTTP 402 (map-protocol-auth-and-results.md, outcome signalling). Velocity is in a newer TranSafe reference build that was never published, but **not** in the published 2.3.2 spec. **Payroc:** no velocity rule, deny list or allow list is documented. Payroc's product descriptions name a Gateway Card Deny List and Gateway Fraud Tools as available (no mechanism or API is documented for either), and name only a **deny** list on the Payroc side. Payroc's documented API-level fraud controls are 3-D Secure, AVS and CVV. **Code that branches on `msoft_code=CARDDENYLIST` or `VELOCITYTHRESHOLD` has nothing to branch on:** a Payroc-side block, if one is configured, can only surface as an ordinary decline (map-protocol-auth-and-results.md, Results rows).
6. **Deny/allow lists: scope, automatic entries, and data.** Entries are shared across the token-sharing group (`tokengroup_id`). Accounts are added automatically on an online decline (profile flag `CARDDENYLIST_DECLINE`, or `carddenylist_decline=yes` on the transaction) and on a failed fraud check, and checked automatically (`CARDDENYLIST_CHECK`, or `carddenylist_check=yes`); the allow list exempts known-good accounts from fraud checks and auto deny-listing. The per-transaction flags have no Payroc request field: drop them from `payment` bodies. Processor-encrypted and processor-token accounts cannot be listed. **The list cannot be moved through the API:** account numbers are stored encrypted and the list report returns `last4` only, and TranSafe has no export action for either list. Re-creating an existing deny list on Payroc needs a TranSafe-side extraction; ask your implementation contact how Payroc moves it.
7. **E2EE and P2PE: TranSafe is the key custodian; on Payroc, Payroc is.** All E2EE and P2PE actions are not in TranSafe's public documentation; most are `action_su` (system-restricted: TranSafe operators), and *Generate Standin Encryption Key* and the five `p2pe=` device actions are `action_admin`. TranSafe generates a Base Derivation Key, shares it with a Key Injection Facility that injects the devices, and decrypts device data with it; validated P2PE adds device provisioning and quarterly inspection logs. Payroc exposes no key-management operation. Its card-present requests carry device-encrypted data identified by the device `model`, `serialNumber` and `dataKsn`; devices are ordered from Payroc (`createTerminalOrder` → order-a-terminal) and listed read-only with their key serial identifier (`searchDevices`). Payroc's product descriptions list P2PE as available on the Payroc Gateway (no API is documented for it). **Hazard: data from a device injected under a TranSafe-generated BDK cannot be decrypted by Payroc unless the key moves or the device is re-injected or replaced.** That is Payroc's device migration, not an API change; Payroc has not published whether TranSafe-injected devices are re-injected, reconfigured in the cloud or swapped; confirm the path with your implementation contact. Do not deactivate a TranSafe BDK (irreversible: no devices injected with an encryption key based on the BDK will be able to process transactions) until every device under it has moved.
8. **Do not use destructive TranSafe calls as migration clean-up.** Payroc's migration terms describe post-migration TranSafe access as read-only for 13 months after each merchant's migration date (with 13 months of history kept) and also as refunds-only for an unstated period; ask your implementation contact which applies to your users and API keys. Either way, the TranSafe users and keys that perform those refunds must survive cutover. *Delete User* also deletes that user's API keys; *Remove API Key* is permanent (a Payroc portal revoke is reversible); BDK and device deactivation are permanent.

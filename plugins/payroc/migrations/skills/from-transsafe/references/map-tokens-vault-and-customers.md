## Cross-cutting facts

Transports, Bearer auth, outcome signalling and the `Idempotency-Key` rule (every Payroc POST and PATCH below needs one) are in [map-protocol-auth-and-results.md](map-protocol-auth-and-results.md). What a TranSafe `token` becomes on Payroc (`secureTokenId` vs `token`, the legacy token id kept in `merchantref`), ACH tokens, token-group scope, `customer_id`, `clientref` and `profile_id` → `processingTerminalId` are in [identifier-translation.md](identifier-translation.md). File-local facts:

1. **Payroc has no customer resource.** No Payroc operation or path manages customers or customer profiles; the only `contacts` resource is the business's points of contact for boarding. Customer data exists on Payroc **only as the `customer` object embedded in each secure token**: `firstName`, `lastName` (60 each), `dateOfBirth`, `referenceNumber` (48), one `billingAddress`, one `shippingAddress` (+ `recipientName`, 50), `contactMethods` (email / phone / mobile / fax), `notificationLanguage`. Payroc does not offer customer profiles today, so do not design around one: keep the customer record in your own system. Payroc also lists TranSafe Customer Tokenization and customer-database users as not ready to migrate yet; if you use either, raise it with your implementation contact before planning a cutover date.
2. **TranSafe's customer database is relational; a TranSafe customer can exist with no token.** A customer has an address book (any number of addresses, with `default_billing_id` / `default_shipping_id`), a `default_token`, and owns tokens through `customer_id`. On Payroc each card is a separate secure token carrying its own copy of one billing and one shipping address. Keep the customer → `secureTokenId` map in your own system.
3. **Address formats differ.** TranSafe `country` is ISO 3166-1 **alpha-3** (`USA`, max 3) and only `address1` is required. A Payroc address requires `address1`, `city`, `state`, `country`, `postalCode`, with `country` **alpha-2** (`US`).
4. **Scope: token group → processing terminal.** Every TranSafe vault and customer query is bounded by the caller's `tokengroup_id`, which may be shared by several merchant profiles. Every Payroc secure-token call is bounded by one `processingTerminalId` in the path. Payroc supports shared tokens, but ask your implementation contact how TranSafe's token-group hierarchy maps onto Payroc terminals, and test it in the test environment, before relying on any group-wide behaviour below. See also the token-scope row in identifier-translation.md.
5. **`save-a-payment-method` does not document `updateSecureToken` (PATCH).** Its endpoint table lists create, list, retrieve, delete and update-account only. Rows that need the PATCH name the skill for the surrounding flow and point to the Payroc *Update saved payment details* guide on docs.payroc.com for the request; the PATCH body is an RFC 6902 operations array, not flat fields.
6. **Token migration is not developer work.** Payroc moves existing stored cards into the Payroc gateway and, as Payroc states (this is not in Payroc's published documentation; confirm it with your implementation contact), puts each legacy TranSafe token id in the imported record's `merchantref`; data migration is out of this skill's scope. What you do in code: stop calling the TranSafe export actions, and look migrated tokens up by the old token id. Which Payroc field and lookup operation expose that id is not confirmed: ask your implementation contact and test the lookup in the test environment. Payroc's published token import covers card data only, and Payroc states that its automated import does not support ACH (not in Payroc's published documentation): assume no ACH token carries over and re-collect bank details unless your implementation contact confirms otherwise. Payroc's published import process runs through the Gateway Team: a GUID, one PGP-encrypted CSV per terminal, up to 100,000 records, about 30 business days, card data only.

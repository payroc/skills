# TranSafe → Payroc: identifier translation and field formats

> **Local snapshot — authoritative for this skill.** Payroc's own cross-cutting mapping of the
> identifiers and field formats a TranSafe integration stores or sends (`ttid`, tokens, customer ids,
> `cardshieldticket`, order references, merchant ids, amounts, expiry dates, timestamps) to their Payroc
> equivalents. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-10-08. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

## Cross-cutting facts

1. **One field, every transport.** KV integrations (libMonetra, XML/JSON envelope, IP/SSL) send the
   same flat keys REST nests in groups (`account_data.token` is KV `token`; `money.amount` is
   `amount`); REST JSON is flattened and lower-cased on arrival. Every row below applies to a KV key of
   the same name.
2. **Every TranSafe value is a string; Payroc amounts are integers.** TranSafe's documentation says
   "All key and values are strings. Even numeric amounts or counts are sent as strings". A numeric JSON
   value gets `500 Unauthorized` on v2 and `401` on v1. Payroc `order.amount` is an int64 in minor
   units, so the type flips in both directions: a string `"1900"` sent to Payroc is a schema violation
   **[inferred]**.
3. **TranSafe spec patterns are not runtime checks.** TranSafe accepts values its own
   patterns forbid: the published `expdate` pattern `(0[1-9]|1[1-2])\d{2}` rejects October (`10`), but
   TranSafe accepts `expdate=1028`; the `ordernum` pattern `[0-9a-zA-Z]+` forbids `-`, but TranSafe
   accepts an `ordernum` containing `-`. Data an integration already stores may violate TranSafe's own spec.
   Size Payroc-side validation for the data you actually hold, not the data the TranSafe spec says you
   could hold.
4. **The lifecycle handle changes shape.** TranSafe's `ttid` is numeric at runtime (15 digits at runtime; the spec allows 1–38 characters from `[a-zA-Z0-9+ _-{}]`). Payroc's `paymentId`
   and `refundId` are **exactly 10 alphanumeric characters** (`M2MJOG6O2Y`). A database column typed as
   an integer for `ttid` cannot hold a Payroc id.
5. **Nothing on Payroc accepts a TranSafe identifier.** No Payroc operation has an
   original-transaction, legacy or migration field that links to a TranSafe record. Merchant-assigned
   fields (`order.orderId`, `customFields`, `secureTokenId`) take any value you send, TranSafe values
   included (rows `FIELD ordernum`, `FIELD clientref`), but Payroc resolves nothing from them. The
   token-import columns `merchantref` (section 2) and `transactionReference` (row `FIELD cof_transid`)
   are the only published places a TranSafe value enters a Payroc record.
6. **Currency.** TranSafe requests can carry an optional **numeric** `money.currency` ("ISO 4217
   3-digit numeric code"; runtime alias `curr`), accepted on the v2 purchase, preauth, refund,
   complete and adjust operations. Most requests omit it and the profile's `currencycode`
   (default `840`) applies. Payroc requires `currency`, as an **alphabetic** code. See the
   `FIELD currency` row.

## 2. Tokens and customers

TranSafe uses **one** value, `token`, both as the path key (`/vault/account/{token}`) and in a payment
(`account_data.token`). Payroc splits these into **two**: `secureTokenId` (merchant-chosen or
gateway-generated, ≤200 characters, the path key) and `token` (gateway-assigned, 12–19 digits, begins
`296753`, Luhn check digit; what a payment sends). A payment response returns both on
`card.secureToken`.

**What the TranSafe token value is.** A numeric string of configurable length 12–19 (default 16), with
a configurable prefix (default `10`) and a check digit. The same formatter produces the API's `token`
and the modern export's `merchantref`, so **`merchantref` is exactly the value the developer stored**.
Token length and prefix are deployment settings; check your own stored tokens.
A TranSafe token can pass the 12–19-character length check on Payroc's `secureTokenPayload.token`
without being a Payroc token, so a mis-port fails at runtime as an unknown token, not as a schema error
**[inferred]**.

**Payroc's published token-import process:**
- Card data only: "You can't migrate bank account details".
- One CSV per terminal, named `<GUID>_<terminal_number>.csv`.
- **At most 100,000 records per file.** This matches TranSafe's 100,000-row export chunk.
- `merchantref`: 1–200 characters, required, "how you identify a stored card after we import it". It
  must be unique within the file **and for the terminal**, and cannot be changed afterwards.
- `cardExpiry` may be MMYY, YYMM, MMYYYY or YYYYMM.
- Import takes about 30 business days.

The import documentation does **not** say which Payroc field `merchantref` becomes. Payroc states
that the legacy token id goes into `merchantref`, but this is not in Payroc's published documentation;
the rows below use it, and mark the `merchantref` → `secureTokenId` step as inferred. Confirm the field and the lookup operation with your
implementation contact before relying on either.

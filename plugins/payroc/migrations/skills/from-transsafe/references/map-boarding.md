> [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in

## Cross-cutting facts

Transport, auth, outcome signalling, `Idempotency-Key` (declared on every Payroc POST and PATCH below; the PUTs `updateContact` and `updateEventSubscription` declare none) and pagination: [map-protocol-auth-and-results.md](map-protocol-auth-and-results.md). `profile_id` → `processingTerminalId` and `group_id`: [identifier-translation.md](identifier-translation.md) (`FIELD profile_id`, `FIELD group_id`; both `config`). File-local facts:

1. **TranSafe boards configuration; Payroc boards an application.** A TranSafe profile becomes usable as soon as it has a route: the merchant's acquiring relationship and processor MID already exist and are typed into the route. None of the TranSafe boarding actions takes owners, tax id, pricing, bank account or a signature (the one near-match is `tax_rate_autopop` on Create/Edit a Profile, a default tax rate, not a tax id). Payroc's `createMerchant` and `createProcessingAccount` submit an **underwritten application**: Payroc "review[s] the merchant's information" and only "after we complete our review and approve" assigns `merchantPlatformId` / `processingAccountId`. A processing account requires `doingBusinessAs`, `owners`, `merchandiseOrServiceSold`, `businessStartDate`, `timezone`, `address`, `contactMethods`, `processing`, `funding`, `pricing` and `signature`; the merchant platform adds `business` (`name`, `taxId`, `contactMethods`, `addresses`, `organizationType`). Then the terminal comes from a terminal order (`createTerminalOrder`), which yields the `processingTerminalId` every transaction needs. So no TranSafe boarding call is a like-for-like port: your code must collect data TranSafe never asked for and wait on an asynchronous approval (`processingAccount.status.changed`).
2. **Existing merchants are moved by Payroc; the boarding API is for new merchants only.** Payroc pulls merchant information and data out of TranSafe and puts it into the Payroc gateway; processors the gateway supports import 1:1 with no action for the merchant, and others are re-boarded by Payroc, with no development work on your side. Payroc states this, but it is not in Payroc's published documentation. So an existing merchant needs **no developer boarding action**, and data migration is out of this skill's scope. Rows below are mapped **for code that keeps boarding new merchants**. Confirm with your implementation contact whether merchants Payroc has migrated appear in your API reads; until you have, treat the read rows as unverified for those merchants (fact 5).
3. **What the Payroc API does not have.** It has no operation for groups, hierarchy, permissions, roles, users, white-label or brands, portfolios or partners, routes or processors, and none to enable, disable, activate, move or merge a merchant platform or processing account. Merchant platforms, processing accounts and processing terminals cannot be edited, suspended or deleted through the API. **Editable sub-resources:** processing-account **contacts** (`updateContact` PUT, `deleteContact`). **Not editable: processing-account owners.** `updateOwner` and `deleteOwner` exist but state "You can't update the details of an owner of a processing account" and "You can't delete an owner of a processing account"; they serve funding-recipient owners only. Do not map a profile edit to `updateOwner` or `deleteOwner`.
4. **Group hierarchy.** A TranSafe group is a hierarchy node that caps its users' permissions, carries flags (`SHARE_TOKENS`, `PUSH_NOTIFICATION`, `ACCOUNT_UPDATER`, `WHITELABEL_BRANDING`, `REQUIRE_MFA`, `MODIFY_SELF`) and white-label contact data. TranSafe documents an **example** flow for adding a merchant: a group for the merchant, users under it, and a profile for the merchant's stores with routes on each profile. It is an example, not an enforced structure (inferred: nothing confirms enforcement), so a real portfolio may differ. Above that sit partner/portfolio groups. Payroc's only container is the **merchant platform**, one level, holding processing accounts, created by `createMerchant` together with its first processing account(s) (`createMerchantAccount` requires `business` and `processingAccounts`). So a **merchant-level** group pairs (loosely) with a merchant platform, and a **partner-level** group pairs with nothing in the API. For portfolios, permissions and white-label, ask your implementation contact what Payroc offers.
5. **Reads on Payroc only see what the API boarded.** `getProcessingTerminal`: "You can retrieve a processing terminal only if the terminal order was created using the Payroc API". `listMerchantPlatforms` returns platforms "linked to your ISV account". The terminal and host-configuration reads are unverified (see `order-a-terminal`): the terminal retrieve call has a known issue and host configuration is not available in the test environment. Payroc moves existing merchants (fact 2); confirm with your implementation contact whether those merchants appear in your reads. Until you have, every read row below is `unverified` on the pairing.
6. **Routes and processors: the partner chooses the processor; routing is Payroc configuration.** A TranSafe route names any enabled processor and carries that processor's MID/TID and other credentials as free processor-specific fields, validated per processor. On Payroc the boarding request carries a **partner-chosen** `processor`: `tsys` or `fiserv`, default `tsys` ("We recommend that you include a value for the processor parameter and not rely on the default value"; also on `createMerchant` via `createMerchantAccount.processingAccounts.items` → `createProcessingAccount`; create-merchant-platform agrees), and per-card-type acquirer ids are partner-supplied in `processing.specialityCards` (AmEx direct, EBT FNS number, WEX, Voyager, Fleet). There is no route, routing or per-card-type split API. The only processor read is `getProcessingTerminalHostConfiguration`, documented for a different audience ("Integrate with this method only if you use your own gateway and want to validate the processor configuration"), whose `processor` discriminator models only `tsys`; rows that read it carry that caveat. For **existing** merchants, processors the Payroc gateway supports import 1:1 with no merchant action; others are re-boarded by Payroc, with no development work on your side. Payroc states this, but it is not in Payroc's published documentation.
7. **Push notifications vs event subscriptions.** TranSafe push = transaction events, batched per endpoint about every 30 s as a JSON array, retried on any non-200 (do not assume a retry limit), optional `Basic` auth, selected by `eventflags` (event kind × card type × declines), and resolved **at transaction time** from every `PUSH_NOTIFICATION`-flagged ancestor-or-self group **plus** the profile's own `pushnotification_id`, so one transaction can notify several endpoints. Payroc event subscriptions: one CloudEvents notification per event, a `Payroc-Secret` header (`secret`, 16–64 chars, required), up to five retries and then an email to `supportEmailAddress`, scoped to the ISV account. **The published event list has four boarding events and no transaction events.** The only Payroc transaction-result webhook is **HPP background validation**, configured in the Self-Care Portal and covering Hosted Payment Page **card** payments only. Payroc does not offer webhooks for transaction events today; ask your implementation contact about availability. If your integration depends on TranSafe push notifications, it is not ready to migrate until they are available. Every push row is `unverified` on the pairing.
8. **Destructive TranSafe calls during migration.** *Remove a Group* deletes the group's users and **all API keys under it**, then purges its tokens, customers and card deny list. *Remove a Profile* deletes its routes, API keys, recurring schedules, **automated-settlement (cron) tasks**, counters, stats, SkyLink data, logo, hosted paypages and terminal-load data, orphans shared tokens, customers and deny-list rows, then purges its **transaction data**, orders, products and bucket stats. Do not run either on TranSafe as "clean-up" until Payroc has finished moving your data.

## Cross-cutting facts

Stated once here; every other file points back to this section instead of repeating it.

1. **There is no Payroc KV transport.** A KV-protocol integration (libMonetra, `<MonetraTrans>` XML/JSON envelope, POST, raw IP/SSL) moves to HTTPS REST with JSON bodies and a Bearer token from the Payroc Identity Service. TranSafe is one action set over several transports: all pairs are strings, object grouping is not evaluated, and every key/value pair is moved to the top level; REST flattens JSON objects into the same flat key-value set the other transports carry. Payroc declares one security scheme, `bearerAuth` (HTTP bearer, JWT), obtained by `POST https://identity.payroc.com/authorize` (the same host for test and live; the API key decides which) with an `x-api-key` header; tokens expire after one hour (`expires_in` 3600). The Payroc API has no KV, XML or socket transport and no form-encoded transaction endpoint: the only non-JSON request body in the public API is one `multipart/form-data` upload (`createProcessingAccountAttachment`, for boarding attachments), and Payroc's authentication documentation notes that some endpoints need another Content-Type. The documented request headers are `Content-Type: application/json`, `Authorization: Bearer` and `Idempotency-Key`.
2. **Outcome signalling differs on every TranSafe transport, and differs again on Payroc.** TranSafe REST v2: `200` = approved, `402` = declined, any other status = TranSafe refused the request (approved `200 OK`, `code=AUTH`; declined `402 Payment Required`, `code=DENY`). REST v1: `200` for every transaction, read `code` (a decline is `200 OK`, `code=DENY`). KV/libMonetra: `code` only; `M_ReturnStatus` is success when `code` is `AUTH` or `SUCCESS`, or when the response is comma-delimited report data. **Payroc `payment` returns `201` whether the card is approved or declined** (its only 2xx response, "We processed the transaction"); read `transactionResult.status` (`ready`/`pending` = success; `declined`/`referral`/`pickup` = unsuccessful; `accepted` ("in progress … we can't confirm the result yet") or `admin` ("under review") = **not approved; do not fulfil**. Payroc documents no follow-up for either: fetching the payment again with `getPayment` (a refund with `getRefund`) until the status changes is **inferred**, and `admin` may be terminal, so escalate to Payroc Integrations) and `transactionResult.responseCode` (`A`/`P` vs `D`/`R`/`C`; `E` = "will process the transaction later": also not approved; do not fulfil, and any follow-up is **inferred** as above). This Payroc-side behaviour is not confirmed on a live request; check it in the test environment. Run a declined-card test in the test environment and confirm your branching before go-live. Result handling must be re-derived, not translated.
3. **TranSafe REST v2 returns HTTP 500 for request-parse failures and for duplicates, keeping the original reason phrase. Retry-on-5xx logic must not be ported.** In practice: v2 with no `Authorization` → `HTTP/1.1 500 Unauthorized`, no `WWW-Authenticate` (v1: `401` + `WWW-Authenticate: Basic`); v2 with `Content-Type: text/plain` → `500 Unsupported Media Type` (v1: `415`); a numeric JSON `amount` → v2 `500 Unauthorized`, v1 `401`, both `code=DENY`, verbiage "json data for key 'amount' could not be read as a string"; a second identical purchase with `duplcheck=yes` → `500 Internal Server Error`, `code=DUPL`, `msoft_code=INT_GENERICFAIL`. A 400, 404 or 405 is expected to come back as HTTP 500 too, like the 401/415 cases above **[inferred]**; treat any v2 500 as possibly permanent. v1 returns 200 unless authentication fails or the request cannot be parsed.
4. **`duplcheck` → `Idempotency-Key`: the control inverts and the opt-out disappears.** TranSafe duplicate checking is opt-in per request (`processing_options.duplcheck=yes|no`, overriding a server default; TranSafe's standard default is **off**). It is a **rejection** of a matching approved/open transaction (account, amount, `ordernum`, optional time window), not a replay. Your live profile may differ from that default: confirm with your implementation contact whether yours has duplicate checking on by default. Payroc's `Idempotency-Key` is declared `required: true`, UUID v4, on every money-moving POST (`payment`, capture, reverse, refund, adjust, `unreferencedRefund`, `verifyCard`, secure-token and subscription creates, …) and on every PATCH; 8 public POSTs declare none (`binLookup`, `balanceCard`, `searchBinInformation`, `getFxRates`, `applePaySessions`, `deactivateSubscription`, `reactivateSubscription`, `deactivatePaymentLink`), although Payroc's idempotency documentation says every POST and PATCH "must include" it (the documentation and the API reference disagree). Omitting it where declared is `400` (`#idempotency-key-missing`); the same key + same URI + same body returns the saved response (7-day retention); the same key with a different URI or body is `409` (`#idempotency-key-in-use`). **"Allow a duplicate" on Payroc is a fresh key, never an omitted header** (omitting it is a 400).
5. **Amounts: decimal strings → integer minor units.** TranSafe `amount` is a string matching `\d*(\.\d{0,2})?`, example `19.92`; all keys and values are strings, even numeric amounts and counts, and a JSON number is rejected (fact 3). Payroc `order.amount` is an `int64` "in the currency's lowest denomination, for example, cents". So `"19.92"` → `1992`, `"19"` → `1900`, `"19.9"` → `1990`.
6. **Currency: Payroc requires it; TranSafe requests normally omit it, but an optional numeric `currency` exists.** TranSafe's money group has an optional `currency` request key, "ISO 4217 3-digit numeric code" (e.g. `124`); "depending on the processor, this code may be required". It is accepted on purchase, preauth (and their `/{ttid}` variants), complete, adjust, refunds and merchandise returns (both with and without `/{ttid}`), and TranSafe does not require it on any of them. The merchant profile carries `currencycode` (ISO 4217 numeric, default `840`). A purchase sent without `currency` is approved. Payroc `order` requires `amount`, `currency` and `orderId`; `currency` is an ISO 4217 **alphabetic** enum (`USD`).

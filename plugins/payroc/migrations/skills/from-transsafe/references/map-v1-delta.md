# TranSafe → Payroc: REST v1 / KVS v8 actions (delta to the v2 rows)

> **Local snapshot — authoritative for this skill.** Payroc's own operation-by-operation mapping from
> the TranSafe REST v1 and KVS v8 actions to the Payroc API. Every action here is a short delta row that
> points (`⇒`) to its REST v2 / KVS v9 twin, which is mapped in full in another reference file, and states
> only what differs. Per-row confidence is carried in the `C` column; the legend is in
> [`_sources.md`](./_sources.md). Last synced: 2026-10-08. Read mappings from this file, not from
> memory — a plausible-sounding mapping that isn't here will look correct in review and fail in
> production.

The text after `⇒` is the twin row's key, copied verbatim. When one v1 action spans several v2 rows, the other twins are named in the Request delta cell. The **V** and **Payroc target** cells are copied from the first twin, except where the v1 call itself behaves differently (Pre-Authorization Completion with `apprcode`; Remove Account and Remove Stored Payment `recurringdel`). Read the twin row for the Payroc request shape and its hazards. The v1 actions that have **no** v2 twin get full rows (no `⇒`).

## Cross-cutting facts

map-protocol-auth-and-results.md and identifier-translation.md apply to v1 as to v2. What is v1-wide is stated here once.

1. **Every v1 / v8 request is translated into a v9 action before it runs.** TranSafe rewrites `action` (and `admin`) into the v9 `action_trans` / `action_admin` / `action_sys` keys, and a REST v1 call becomes the same v8 keys (e.g. `action=preauthcomplete`). So the **v2 twin's behaviour applies**, and a v1 difference can only come from one of four places: (a) a key rename on the way in (`sub` → `route_id`, `merchinfo` → `merch_info`, `recurringadd=customeraddress` → `customer_add=customer_address`, …); (b) a **complex operation** that runs several v9 actions for one v8 call (`recurringadd`/`edit`/`del`/`list` on tokens and schedules, `trandetail`); (c) an **output filter** that renames v9 result columns back to v8 names; (d) a **refusal**: some v8 actions "have been removed. Use CRON". This holds for every action in this file. The v9 behaviour behind the translation is described in the twin rows, not here.
2. **Outcome signalling.** REST v1 returns **HTTP 200 for every transaction, approved or declined** (the v1 documentation says "a HTTP 200 repsonse code will be returned for all transactions"; a declined sale returns `200 OK` with `code=DENY`); v2 returns 402; Payroc returns 201 either way and is read from `transactionResult.status` (map-protocol-auth-and-results.md, Results rows). On v1 the 200 is filled only when no status was already set, and is overridden only for authentication failure (401). Request-parse failures keep their 4xx: 401 with no authentication, 415 for a wrong content type, and 401 for a numeric JSON `amount` (a data-parse failure that v1 reports as 401). So a v1 **admin** failure (a removed-action refusal, a missing record) is expected to be HTTP 200 with `code=DENY`: TranSafe is expected to behave this way for admin actions; test before relying on it. A v8 refusal carries `code=DENY`, `msoft_code` = the V8EMULATION data error, and the reason in `verbiage`. Rows below repeat this only where it changes code (transaction rows).
3. **Authentication.** The v1 documentation says "Only HTTP Basic authentication is currently supported", with the username's colons written as pipes (`user|profile:password`). `X-API-KEY-ID` / `X-API-KEY` are accepted on `/api/v1` as on v2: on v1, a request with no authentication returns 401 and a wrong API key fails as `ACCT_AUTHFAILED`; treat API-key auth on v1 as unconfirmed and use HTTP Basic until you have tested it. KV8 only: `auth-as` is folded into `username::auth-as`, and a `MADMIN` username makes the emulation try master-admin verbs first. Payroc target for all of these: map-protocol-auth-and-results.md, Authentication rows.
4. **v1 is unpublished.** The main TranSafe documentation no longer links the v1 reference (the UniTerm page still does), and the page returns 404. Integrators may hold a saved copy of the old page.
5. **Aliases a grep must find.** v8 `action=sale` also accepts `action=redemption` and `action=purchase` (per the v8 documentation); v8 `action=return` also accepts `action=refund`, `action=reload`, `action=credit` (documentation and TranSafe agree). **TranSafe differs from its documentation for `purchase`:** `action=purchase` is documented, but TranSafe is expected to refuse it ("Unrecognized v8 emulation action"); use `action=sale` or `action=redemption`, and test if you rely on `purchase`. Hidden alias: v8 `action=force` = `action=preauthcomplete`, see Pre-Authorization Completion. v7 spellings still accepted: `action=admin admin=recurring recurring=add|edit|del|delete|hist|history|list|clearhist|clear|recurringclear` and `admin=ub` (= `bt`).
6. **Recurring model.** In v8 a scheduled payment **is** a stored token with a schedule attached, addressed by `token`; in v9 the token and the schedule are separate records, the schedule addressed by its own `id`. The v8 emulation bridges this with complex operations that touch both (Scheduled Payments and Account Vault rows). Identifier consequences: identifier-translation.md.
7. **Parameter differences common to many rows.** In most rows the `inferred` half of `C` means the v1 and v2 field names line up; it does not mean the behaviour was confirmed end to end, so test the specific behaviour before go-live. v2 adds `profile_id` (act on a sub-profile) to almost every action and `order_id`, `rcpt_user_notes` to the transaction verbs; v1 has none of them. v1 `ptrannum` is not v1-specific: every version renames it to `ordernum` on receipt. KV8 `acct_type` is merged into `accounttype`. Some TranSafe deployments add `phard_code=UNKNOWN` to every v8 response; tolerate the field.
8. **Runtime-only v8 verbs (no rows).** The v8 emulation also accepts transaction verbs that are not documented in the v8 reference: `tip` (→ v9 `TIP`), `settlerfr`, `toreversal`, `termload`, `interacmac`, `emvcomplete`, `registerclient`, the EBT verbs `ebtfssale`, `ebtfsreturn`, `ebtfsvoucher`, `ebtfsbalance`, `ebtcbsale`, `ebtcbcash`, `ebtcbbalance`, the check verbs `checkverify`, `checkconvonly`, `checkconvvrfy`, `checkconvguar`, `checkconvover`, `checkimageupload`, and `altpaymentinit`; `ivrreq`/`ivrresp` are expected to be refused ("has been removed"); check whether your integration sends them. A KV8 caller sending one is translated to the v9 action of the same name, so use that action's v2 row where one exists: EBT → the EBT rows of map-gift-ebt-check-altpay.md (voucher and cash-withdrawal: that file's fact 2), check conversion and verification verbs → its Check rows (`checkconvvrfy`: that file's fact 7 and its conversion-with-verification row), `altpaymentinit` → its Alternate Payment rows. `tip`, `settlerfr`, `toreversal`, `termload`, `interacmac`, `emvcomplete`, `registerclient` and `checkimageupload` have no v2 row in any reference file: do not guess a mapping; share a request sample and escalate to your implementation contact. (`checkimageupload` is a financial transaction that uploads a check image against a prior conversion. Its nearest relatives are the Store Check row in map-card-transactions.md, `image_add image_type=check` (`none`), and the Check rows, and neither is its twin.)
9. **v1-specific hazards at a glance** (each is in its row):
   - Remove Stored Payment / Remove Account (v8 `recurringdel`) delete the card and the schedule together; v2 deletes one or the other.
   - Pre-Authorization Completion with `apprcode` becomes a FORCE (offline/voice sale), and `action=force` is a hidden v8 alias. The FORCE writes a new record and leaves the pre-authorization uncompleted; the pre-authorization's hold is expected to stay open until it expires [inferred]; confirm with a test authorization. Port it as a new sale plus completing or reversing the pre-authorization. The nearest Payroc target is `payment` + `offlineProcessing` (`offlineApproval`, `approvalCode`), documented for offline-terminal transactions, not voice authorisations: confirm with Payroc Integrations before porting.
   - `action=reload` and `action=redemption` are the gift-card names of refund and sale; on a gift card they have no Payroc target.
   - `action=purchase` is a documented v8 alias that TranSafe is expected to refuse.
   - Force-Settle Batch is a clear, not a settle.
   - v1 Get Transaction Details can send email/SMS receipts as a side effect of a read.
   - Scheduled payments are addressed by token on v1; a v1 schedule edit clears skip-missed unless resent.
   - v1 reports and merchant reads return v8 column names, so v1 parsers must be re-derived against the Payroc shapes, not against v2.
   - HTTP 200 on every v1 transaction decline (and, expected but untested, on v1 admin failures), versus 402 on v2 and 201 on Payroc.

## The verdicts mean different things — do not collapse them

- **`none` — no Payroc equivalent.** The target cell is `—`; the row gives an alternative or an
  escalation route. Check the `C` badge before treating the capability as lost: some `none` rows are
  checked absences, others rest on a point not yet confirmed.
- **`config` — the capability survives; it is no longer something you *call*.** Payroc configures it
  at boarding or on request, or the work moves outside the API. The row names the route to ask
  (usually your Payroc implementation contact). A `config` row is not a loss: the capability survives, but Payroc
  configures it rather than you calling it.
- **`OUT` (verdict `—`) — you cannot call it today.** The action is internal-only in TranSafe (not in its public documentation), or
  this guide excludes it. That is different from "no equivalent".

**How to read a row.** Rows are reproduced from their own reference file — hedges, two-sidedness and
confidence badges included — not summarised. **A row's presence in this register is not itself a
confidence signal:** a `none` row can be `verified` (a checked absence) or `unverified` (a point
not yet confirmed). Read the badge. **Each copied row comes from the domain reference named in its heading; if a row here differs
from that file, treat the domain file as current.** A hit in a GROUP or OUT row
answers for every member action listed in that row's key. If your call is in neither this file nor its domain file, no mapping is documented for it: send a
request sample, and do not assume a Payroc equivalent.

## Cross-cutting facts

1. **Read map-protocol-auth-and-results.md and identifier-translation.md first.** Nothing here repeats their facts.
2. **What the Payroc API exposes for each area.** Each GROUP row's "No Payroc …" claim rests on one of these:

   | Concept | What the Payroc API has | Reading |
   |---|---|---|
   | Catalogue | No resource or path names a product, item, SKU, catalogue or inventory, and there is no modifier concept. Payroc's "tax rates" are a per-terminal setting and a per-payment tax; its "discount" is a per-line `discountRate` and boarding pricing; "SKU" appears only as Level 3 `productCode` guidance | No catalogue resource |
   | Orders and invoices | No invoice resource. The only two `order` paths are hardware terminal orders; `invoice` appears only as subscription counters and a terminal `invoiceNumberPrompt` | `order` is an attribute of one payment; payment links are the invoice-style substitute |
   | Order reporting | No order, item or aging report | Reporting is payment-level only |
   | Atomic bulk operations | No bulk operation (the portal has a Bulk Payments feature, which is not an API) | No bulk API |
   | Multi-merchant settlement | No big-batch or aggregation operation. Of Payroc's three batch paths, only `closeBatch` is per terminal; the two batch reads are by date or by batch id, and none aggregates | No aggregation |
   | SkyLink / licensing | No SkyLink or licence operation | No licence operation |

3. **Payroc's product answers are not API mappings.** Roc Terminal+ (inventory management) and Roc Services (catalogues, estimates and invoices) are no-code applications that Payroc sets up. Offering one means the merchant changes product, which is a commercial decision, not something a code port decides.
4. **Adaptive Routing, CSV Transaction Import and advanced Analytics.** These three are TranSafe product features with no API call; if a merchant depends on one, it is a product conversation, not something a code port can map. Your options are to adapt the merchant's workflow, find a third-party tool, or raise it with your implementation contact.

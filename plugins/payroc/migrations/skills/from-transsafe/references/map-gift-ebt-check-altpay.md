# TranSafe → Payroc: gift, EBT, check and alternate payment methods (REST v2 / KVS v9)

> **Local snapshot — authoritative for this skill.** Payroc's own action-by-action mapping from the
> TranSafe REST v2 / KVS v9 Gift, EBT, Check and Alternate Payment Method actions to the Payroc API.
> Per-row confidence is carried in the `C` column; the legend is in [`_sources.md`](./_sources.md).
> Last synced: 2026-11-03. Read mappings from this file, not from memory — a plausible-sounding
> mapping that isn't here will look correct in review and fail in production.

## Cross-cutting facts

1. **Stated elsewhere, not repeated per row.**
   - `map-protocol-auth-and-results.md`: KV → HTTPS + Bearer. TranSafe v2 answers 200 on approval and 402 on decline; Payroc answers **201 on approval and on decline** for `payment` and `unreferencedRefund` (read `transactionResult.status`), while a referenced `refundPayment` answers **200** with the payment. `duplcheck` → `Idempotency-Key`. Decimal-string amounts → integer minor units, `+order.currency`.
   - `identifier-translation.md`: `ttid` → `paymentId`, and **a pre-cutover `ttid` resolves on no Payroc endpoint**. `profile_id` → `processingTerminalId`. `cardshieldticket` → `singleUseToken`. `FIELD token` (ACH) is `none`: the automated token import does not support ACH.
   - `map-card-transactions.md` defines the **standard envelope** (`Idempotency-Key`, `processingTerminalId`, minor units, `order.orderId` + `order.currency` on new payments and unreferenced refunds) and maps `nsf` → `order.acceptPartialAmount`. Rows below say "standard envelope".

2. **EBT: Payroc has it.** `ebtDetails` (`benefitCategory` `cash` \| `foodStamp`, optional `withdrawal`) and `ebtDetailsWithVoucher` (`voucher.approvalCode`, `voucher.serialNumber`) are attached to the `singleUseToken`, EMV (`icc`), keyed and swiped card variants of the Payroc payment method, so they reach `payment`, `unreferencedRefund` (`refundMethod` = `cardPayload`) and `balanceCard`. They are **not** available on `secureTokenPayload` or `rawCardDetails`. The response subtype `transactionResult.ebtType` names the EBT type. Type by type:

   | TranSafe action | Payroc `ebtType` | Note |
   |---|---|---|
   | `ebtfssale` (food purchase) | `foodStampPurchase` | row below |
   | `ebtfsreturn` (food refund) | `foodStampReturn` | row below |
   | `ebtfsbalance` (food balance) | `foodStampBalanceInquiry` | row below (`balanceCard`) |
   | `ebtcbsale` (cash purchase) | `cashPurchase` | row below |
   | `ebtcbbalance` (cash balance) | `cashBalanceInquiry` | row below (`balanceCard`) |
   | — (TranSafe type `EBTFSVOUCHER`, no documented action) | `foodStampVoucherPurchase`, `foodStampVoucherReturn` | TranSafe does not document this as an action; its API reference lists it only as a permission value. A caller that sends the raw `action_trans` value may still reach it (**[inferred]**; see below), so check whether your integration sends this type. If it does → `ebtDetailsWithVoucher` **[inferred]** |
   | — (TranSafe type `EBTCBCASH`, no documented action) | `cashWithdrawal` | As the voucher row; if your integration sends it → `ebtDetails.withdrawal` **[inferred]** |
   | — | `cashPurchaseWithCashback` | Payroc-only. No LOSS |

   TranSafe does not document `EBTFSVOUCHER` and `EBTCBCASH` as actions; its API reference lists them only as permission values (`EBTFSVOUCHER`, "food voucher (paper food stamps) purchase"; `EBTCBCASH`, "cash withdrawal"). A caller that sends the raw `action_trans` value may still reach them **[inferred; not confirmed on a live request]**, so check whether your integration does. **No TranSafe EBT type is missing on Payroc.** Neither side has an EBT cash refund. Take `ebtDetails` and `pinDetails` from the Payroc API reference; `run-a-card-sale` does not cover them. `refund-a-card-payment` covers EBT only as a list filter and the `ebtType` response field. `check-ebt-balance` covers balances. `integrate-payroc-cloud` carries `ebtDetails` on device payment instructions.

3. **Gift: absent on Payroc.** The Payroc API has no gift-card operation. It has no operation that activates, loads, redeems, refunds or cashes out a stored-value balance, and no gift tender on `payment`. The Payroc API has no gift-card operation of any kind. `isPrepaid`, reloadable and anonymous-prepaid flags on BIN information describe open-loop cards, and `storedValue` / `privateLabel` card-type labels in settlement reporting are labels, not operations. The nearest operation is `getClosedLoop` (`GET /closed-loop-reads/{closedLoopReadId}`, see `integrate-payroc-cloud`): it returns the "unstructured payload" a Payroc Cloud device read from a closed-loop card, such as a MiFare UID. It is **a read, not a ledger**, and it is not a target for any row below. Payroc does not offer an equivalent to TranSafe gift cards, so **every gift row needs a decision, and you can take it yourself. The options are: leave gift cards off Payroc and keep them on TranSafe, move them to a third-party gift provider, or do not migrate that merchant yet.** A third-party gift provider means planning a separate integration. Your implementation contact can help with the commercial side, but that is one route, not a gate. What happens to balances on cards already issued, and to cash-out requests after cutover, has to be settled before cutover **[inferred; unconfirmed]**; ask about them before cutover.

4. **Gift, PayPal and EBT tender on the generic actions (`map-card-transactions.md` rows).** TranSafe also does gift through the ordinary actions: `sale`, `refund` (TranSafe treats an unlinked refund to a gift card as a **reload**, to which the unlinked-refund permission does not apply; Payroc has no gift reload, so this path has no equivalent) and `balanceinq` (`map-card-transactions.md` maps it `none`). On Payroc, each of those has no target **when the card is a gift card**, for the reason in fact 3. A purchase with `account=PAYPAL|TOKEN|…` or `PAYPAL|AGREEMENT|…` has no target either (PayPal rows). Do not port those branches to `payment` or `unreferencedRefund`.

5. **Token export hazard (gift and PayPal tokens).** The modern TranSafe export splits tokens by one test: the ACH file takes ACH card types, and the "cc" file takes **every other card type**. That includes PayPal Express Checkout billing agreements and gift cards (gift `activate`, `issue` and `merchreturn` may tokenize). Inspect what such a row holds in `cardNumber`; do not assume it is a usable card number. Payroc's import is card-only (`identifier-translation.md`). Filter gift and PayPal tokens out of the "cc" file before import, and plan for those stored payment methods ending at cutover **[verified: TranSafe side; inferred: effect on import]**.

6. **Check is not ACH conversion-ready on Payroc.** TranSafe's Check group is not in its public API reference; confirm whether your integration calls it. It sends a check read by a MICR reader to a check-service processor. **On the Echo processor** it uses a service code per action: `checkverify` `7`, `checkconvonly` `7C`, conversion-with-verification `7V`, `checkconvguar` `7G`, `checkconvover` `71`. Verification uses a separate verification merchant id. Other check processors differ: Certegy sends a product type (`CN` for `checkconvonly`, `CG`, `AG`) and supports neither `CHECKCONVVRFY` nor `CHECKCONVOVER`; TeleCheck supports `CHECKCONVVRFY` and `CHECKVERIFY` but not `CHECKCONVONLY`. TranSafe refuses an unsupported check type before it reaches the processor **[inferred; not confirmed on a live request]**. Payroc's only bank-debit rail is the ACH bank transfer: `bankTransferPayment` with `achPayload`, which requires `routingNumber` (9 digits), `accountNumber` (4–17 digits), `nameOnAccount`, and `secCode` ∈ {`web`, `tel`, `ccd`, `ppd`}. The Payroc reference describes `secCode` as "mandatory for ACH payments and unreferenced refunds", though the schema's `required` list has only type, accountNumber, nameOnAccount and routingNumber. The Payroc API has no MICR capture, no check number, no conversion SEC code, and no guarantee or override concept. **It is the same rail (an ACH debit) with different authorisation.** A converted check is authorised by the presented paper check at the point of sale. A Payroc ACH debit is authorised under one of four SEC codes, none of which names check conversion. Which SEC code a merchant may lawfully use for a former check-conversion flow is a compliance decision: raise it with your implementation contact and your own compliance advisers, and do not default to `ppd`. Gate: ACH must be enabled on the terminal; confirm enablement with your implementation contact. `tokenize=yes` on a check conversion creates **no** vault token: TranSafe does not tokenise check transaction types, and check transactions are check card type, not ACH. Returns: Payroc reports `status: returned` with a `returns` object and offers `representBankTransferPayment` / `closeBankTransferPayment` → take-an-ach-payment, refund-an-ach-payment.

7. **The v9 `checkconvonly` collision.** Two REST v2 routes share `action_trans=checkconvonly`. On TranSafe REST v2, both `/transaction/check/conversion` and `/transaction/check/conversion/verify` send **`checkconvonly`**, so the "Conversion With Verification" endpoint runs a **plain conversion** on Echo (`7C`, not `7V`) and on Certegy (`CN`; Certegy has no verified conversion), and is **refused** on TeleCheck, which does not accept `checkconvonly` (fact 6). The documented KV pair (`checkconvonly`) has no discriminator either, and on TeleCheck it is refused (fact 6). TranSafe has a separate verified-conversion type, `CHECKCONVVRFY` (service code `7V` on Echo), reachable through `action_trans=checkconvvrfy`, which TranSafe does not document as an action (its API reference lists `CHECKCONVVRFY`, "Check verification and conversion", only as a permission value), and through v8 `action=checkconvvrfy` **[inferred for v9; not confirmed on a live request]**. The defect is therefore in TranSafe's REST v2 routing. An integrator who believes their REST checks were verified may be wrong. Not confirmed on a live request: test a verification call in your environment, and confirm with your implementation contact which TranSafe version your environment runs.

## Hazards at a glance

- The REST "conversion with verification" endpoint and the documented KV pair both run a plain conversion on Echo and Certegy, and are refused on TeleCheck (facts 6-7; not confirmed on a live request, so test in your environment). Only the KV `checkconvvrfy`, which TranSafe does not document as an action (its API reference lists it only as a permission value), verifies: Echo's `7V`, or TeleCheck in its own format; Certegy refuses it (fact 6).
- An EBT payment without `ebtDetails` is a valid debit sale on Payroc, so take `ebtDetails` from the Payroc API reference; run-a-card-sale does not cover it (fact 2).
- The EBT balance response is an array keyed by `benefitCategory`, not one value.
- No SEC code fits check conversion, so the choice is a compliance decision to raise with your implementation contact (fact 6).
- Gift and PayPal tokens land in the "cc" export file (fact 5).
- Gift balances already issued, and state cash-out obligations, outlive TranSafe (fact 3).
- Which check processor each check-using merchant is on (Echo, Certegy or TeleCheck) changes the behaviour (fact 6); confirm it with your implementation contact.
- Test in the test environment whether Payroc accepts an EBT referenced refund without a PIN.
- Inspect any gift or PayPal token rows in the "cc" export and exclude them before import (fact 5).

# TranSafe → Payroc: card transactions, details, receipts, Level 3 and images (REST v2 / KVS v9)

> TranSafe REST v2 / KVS v9 card-transaction actions (Transactions, Transaction Details, Transaction
> Receipts, Level 3, Image) to the Payroc API. Per-row confidence is carried in the `C` column; the
> legend is in [`_sources.md`](./_sources.md). Last synced: 2026-11-03. Read mappings from this file,
> not from memory — a plausible-sounding mapping that isn't here will look correct in review and fail
> in production.

## Cross-cutting facts

1. **Stated elsewhere, not repeated per row.** `map-protocol-auth-and-results.md`: KV → HTTPS + Bearer; outcome signalling (TranSafe v2 200/402 vs Payroc **201 on approval and on decline**: read `transactionResult.status`); v2 500s; `duplcheck` → `Idempotency-Key` (required on every money-moving Payroc POST and every PATCH, a fresh key per logical operation, the same key on a retry; `binLookup` and `balanceCard` declare none); decimal-string amounts → integer minor units; `+order.currency`. `identifier-translation.md`: `ttid` → `paymentId` (payments) or `refundId` (refunds); **a pre-cutover `ttid` resolves on no Payroc endpoint**, so open preauths are completed or reversed on TranSafe before cutover (do not plan around a TranSafe switch-off date; ask your implementation contact whether one has been set for your merchants); `profile_id` → `processingTerminalId`; `ordernum` → `order.orderId` (≤24 characters); tokens and `cardshieldticket` → `secureToken` / `singleUseToken` (confirm with your implementation contact which Payroc field and lookup expose an imported token's legacy id).
2. **Standard request envelope.** Every money-moving Payroc call below needs, beyond the row's own delta: `Idempotency-Key`, `processingTerminalId` where the schema has it (`profile_id` in `identifier-translation.md`), and integer minor-unit amounts. New payments and unreferenced refunds also need `order.orderId` and `order.currency`. Rows say "standard envelope" instead of repeating this. TranSafe follow-ups on `/transaction/{ttid}...` are `PATCH` or `DELETE`, except the linked refund, the merchandise return and the repeat purchase and preauth, which are `POST`s; every Payroc follow-up is a `POST` on `/payments/{paymentId}/...` or `/refunds/{refundId}/...` with a JSON body.
3. **Follow-up amounts: what the number means.** A TranSafe follow-up that omits `amount` inherits the original's amount: TranSafe fills `amount`, `examount`, `tax` and the other amounts from the original transaction when a follow-up omits them (every follow-up except sale, tip, preauth, cash-out and card type, which inherit nothing, and void, which always takes the original's amounts).

   | Follow-up | TranSafe `amount` means | Payroc `amount` means | Port rule |
   |---|---|---|---|
   | Reversal | **final amount to be settled** | **amount to reverse** | send authorised − TranSafe amount; omit for a full reversal |
   | Incremental | new total | `orderAdjustment.amount`, "Total amount of the transaction" | same number |
   | Complete / capture | amount to settle; omitted = authorised | amount to capture; omitted = total | same number; to go above the authorisation, adjust first (the Payroc API reference's instruction; the guide calls it a recommendation, Completion row) |
   | Linked refund | amount to refund; omitted = original | amount to refund, **required** | always send it |
   | Adjust | new total (`money.amount` is the total) | new total | same number |
4. **Held funds.** TranSafe has two held states: a `preauth` (not batched until completed) and a `sale` sent with `capture=no`, documented only in the capture action's description, not as a sale parameter (a credit sale counts as captured when `capture` is empty or true). Payroc has one: `payment` with `autoCapture: false` → `status: pending`, defined as "We added the payment to the open batch, but we don't collect the funds until the merchant captures the transaction", which can become `expired`. Pre-auth is an account entitlement on Payroc.
5. **Tips.** A tip sent as `examount` is **inside** `amount`: TranSafe refuses `examount` > `amount` ("EXAMOUNT MUST BE >= 0.00 AND <= AMOUNT") and subtracts the tip from `amount` to find the taxable base. On Payroc keep `order.amount` as the total and put the tip in `order.breakdown.tip` (`type: fixedAmount`, `amount`); `breakdown` requires `subtotal`. A tip after authorisation is an `adjustPayment` (`adjustments[].type: order` with `breakdown.tip`).
6. **Partial approvals.** TranSafe `nsf` defaults to `no` for non-gift cards. A partial approval with `nsf` not true is **reversed internally** and returned as a decline with `msoft_code=NSFAUTODENY`; for card-present credit TranSafe always tells the processor `nsf=yes` and reverses afterwards. Payroc `order.acceptPartialAmount` defaults to `false` ("our gateway declines the payment"); a partial approval is `responseCode: P` with `authorizedAmount` below the request. So `nsf=yes` → `acceptPartialAmount: true`, and the default ports unchanged.
7. **Void and reversal become one Payroc call.** `reversePayment` is "also known as voiding a payment". TranSafe's void is a weaker fallback: full only, possibly offline, may not release the hold. See the two rows.
8. **Absences.** The Payroc API has no transaction-receipt operation, no SMS sharing, no line-item resource, no image store or list, no lodging fields, and no credit or debit balance inquiry (each restated in its row). The Payroc API has no line-item, image-store or receipt operation; its only signature operations are the three Payroc Cloud signature operations.
